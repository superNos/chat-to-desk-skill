## Purpose

根据已校准的工作模型，为每个用户设计并搭建只包含其真实工作所需内容的可交互本机工作台，并用可审阅的工作台说明解释每项设计的依据。

## ADDED Requirements

### Requirement: 主要产出是可交互的本机工作台
技能 SHALL 要求 Agent 的主要产出是一个用户在本机浏览器里打开的可交互工作台，用户在其中能够发起新工作、继续某件工作、修改某个结果，并看到每件事的状态和 Agent 返回的结果。工作模型、工作台说明、交接文字等 Markdown 或文本内容 MUST 只作为工作台的数据、说明或导出内容，MUST NOT 代替工作台交付。只有用户明确表示不要工作台时，Agent 才可以停在设计或说明阶段。

#### Scenario: Agent 想用一份文档代替工作台
- **WHEN** 用户的工作模型只支持一两项功能，Agent 考虑交付一份“常用说明”文档
- **THEN** Agent 仍然搭建一个工作台，把常用说明作为工作台里可查看和可带入交接的内容，而不是只交付文档

#### Scenario: 用户明确不要工作台
- **WHEN** 用户在看过设计草案后说“我只要这份说明，不要页面”
- **THEN** Agent 按用户决定只交付说明，并在工作台说明中记录这是用户的选择

#### Scenario: 交给用户前走一遍
- **WHEN** Agent 搭好工作台准备交给用户
- **THEN** Agent 在页面上用一条试用内容完成一次“发起 → 看到状态 → 得到结果”，确认结果出现在对应位置、状态变化正确，并告诉用户怎么再次打开


### Requirement: 每个工作台元素都能追溯到已确认的工作
技能 SHALL 要求工作台中的每个元素（输入框、对象、字段、状态、结果查看、确认动作、背景资料等）在工作台说明中写明依据，依据 MUST 指向工作模型中已确认、已修正或已限定范围的条目。没有依据的元素 MUST 被删除或作为待确认建议单独列出，不得进入试用版本。

#### Scenario: 设计中出现没有依据的元素
- **WHEN** Agent 起草设计时想加一个“本周统计图”，但工作模型中没有用户查看统计的证据
- **THEN** 该元素不进入工作台；如 Agent 认为有价值，只能作为待确认建议提出并说明缺少的证据

#### Scenario: 依据被否定后
- **WHEN** 某个元素依据的工作模型条目被用户否定
- **THEN** Agent 把该元素标为待移除，并在下一次调整中向用户确认移除

### Requirement: 不使用默认模板
技能 SHALL 禁止把任务卡、待办清单、看板、周报、统计图、仪表盘或任何固定页面结构作为默认起点。这些形式只有在工作证据和用户确认支持时 MUST 才能出现，且名称和字段 SHALL 使用用户自己的工作语言。技能自带的案例 MUST 标明只用于说明推理差异，不得被复制为新用户的方案。

#### Scenario: 非开发用户的工作台
- **WHEN** 一位教师的工作模型显示她主要需要把家长消息整理成回复草稿
- **THEN** 工作台围绕“家长消息 → 回复草稿 → 由她本人发送”设计，不出现任务编号、开发状态、提交确认等开发总控元素

#### Scenario: 证据确实支持某种常见形式
- **WHEN** 用户的历史反复出现按阶段推进多件工作并逐件查看进度
- **THEN** 工作台可以包含按阶段排列的视图，但阶段名称来自用户实际使用的说法，并在工作台说明中写明依据

### Requirement: 证据很少时给最小工作台
技能 SHALL 把结论分为“需要工作台”“小工作台”“暂不需要复杂工作台”三档。当工作模型中没有足够的重复工作、跟进需求或结果查找困难时，Agent MUST 给出“暂不需要复杂工作台”的结论和理由，并且仍然搭建一个最小工作台：只含一两个与证据相符的元素，通常是一个发起工作的入口和一处找回结果的地方。“暂不需要复杂工作台” MUST 表示功能少，MUST NOT 表示不做工作台；Agent MUST NOT 以“文档更轻”为理由不搭工作台，也 MUST NOT 为了显得完整而加入没有证据的元素。

#### Scenario: 历史只有零散一次性问题
- **WHEN** 授权历史中的对话主题彼此无关，几乎没有重复说明或跟进
- **THEN** Agent 告诉用户暂不需要复杂工作台并说明依据，搭一个只有发起入口和结果找回处的最小工作台，并说明出现哪些情况后值得再加功能

### Requirement: 工作台说明可审阅
技能 SHALL 要求 Agent 为每个设计维护一份用户可读的工作台说明，至少包含：结论、页面上每个元素及其依据、每个输入的去向、结果回到哪里、状态如何显示、哪些动作需要每次单独确认、平台能力核实情况、怎么打开工作台、试用范围和调整记录。工作台说明 MUST 用用户能读懂的语言书写。

#### Scenario: 用户询问某个按钮为什么存在
- **WHEN** 用户问“为什么有‘按客户找回终稿’这个入口”
- **THEN** Agent 根据工作台说明回答它对应的工作模型条目和证据

### Requirement: 先确认设计再搭建，并从小范围试用开始
技能 SHALL 要求 Agent 在搭建前向用户展示设计草案并取得确认。首个可用版本 MUST 只覆盖用户确认的最重要的一到三类工作；其余内容留在后续调整中。页面、区域、工作对象、字段、输入框、操作和状态 SHALL 根据该用户的工作台说明逐项生成；技能 MUST NOT 内置任何职业或任何布局的默认页面。页面和配置 MUST 放在用户指定的本机目录，不放进技能目录。

#### Scenario: 用户想一次做全
- **WHEN** 用户确认了六类工作并希望全部做进工作台
- **THEN** Agent 说明先试用最重要的部分的理由，由用户选择首批范围；用户坚持全部纳入时，按用户决定执行并在说明中记录

#### Scenario: 已有的开发总控工具作为案例
- **WHEN** 用户的已确认工作是在一个总控对话中长期分派多项开发任务并跟进复核和提交
- **THEN** Agent 可以把用户已有的开发任务台账一类工具作为同类工作的一种实现提出，让用户决定是否采用，但不得把它推荐给工作模型不同的用户

### Requirement: 不同用户得到不同工作台
技能 SHALL 提供多组差异明显的虚构用户历史和检查方法，用于验证 Agent 按证据设计。对差异明显的历史，Agent 产出的工作台元素、对象和流程 MUST 随证据不同而不同；任一产出中的元素都 MUST 能追溯到该用户自己的证据。

#### Scenario: 用多组虚构历史做差异测试
- **WHEN** 评估者用同一技能分别处理多组差异明显的虚构历史，其中包含非开发岗位、一次只做一件事的开发者和零散使用者
- **THEN** 每份工作台说明的元素各自追溯到本组证据，零散使用组得出暂不需要复杂工作台并只有最小工作台，开发者组不被默认推荐多 Agent 开发任务台账，且不存在一组照搬另一组的元素

#### Scenario: 两个非开发用户的前向演示
- **WHEN** 评估者让两个互不相通的全新会话分别按同一技能处理班主任和业务分析师的虚构历史，并真实启动各自的工作台
- **THEN** 两个工作台在工作对象、输入、操作、状态和结果回写上存在可追溯到各自证据的差异，每个工作台都在页面上完成过一次发起、看到状态和得到结果
