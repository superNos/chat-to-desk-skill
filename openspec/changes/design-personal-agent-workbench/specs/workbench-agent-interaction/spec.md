## Purpose

规定用户通过工作台向 Agent 下发工作、继续工作和取回结果时共同遵守的约定，包括输入去向、交接降级、结果回写、状态展示、单次确认和平台能力核实。

## ADDED Requirements

### Requirement: 每个输入都有明确去向
技能 SHALL 要求工作台的每个输入在提交前明确属于以下之一：开始一项新工作、继续某项已有工作、修改某个已有结果。去向为继续或修改时，MUST 指明对应的那项工作或那个结果。去向无法确定时，工作台或 Agent MUST 先询问，不得猜测。

#### Scenario: 补充要求指向已有工作
- **WHEN** 用户在某份稿件旁的输入框写“第三段语气再正式一点”
- **THEN** 这条输入被交给处理该稿件的工作，结果回到这份稿件，而不是新开一项工作

#### Scenario: 去向不明
- **WHEN** 用户在通用输入框写“把上次那个改一下”，且存在多个可能的“上次”
- **THEN** 工作台列出候选并请用户选择，确认前不发送

### Requirement: 能交给 Agent，不支持时生成交接内容
技能 SHALL 要求工作台在平台能力已核实时把输入交给对应 Agent 对话；能力不支持或未核实时，MUST 生成可直接复制的交接内容（包含去向、背景、要求和期望结果），并明确显示“需手动完成”。工作台 MUST NOT 把生成交接内容显示为已发送。

#### Scenario: 平台无法自动发起工作
- **WHEN** 用户的平台没有已核实的发起工作能力
- **THEN** 工作台生成一段可复制的交接内容，状态显示为需手动完成，用户粘贴发送后才可改为已发送

#### Scenario: 手动交接同样需要材料授权
- **WHEN** 用户尚未授权把某类材料交给 Agent，而交接内容需要包含这类材料
- **THEN** Agent 在生成交接内容前说明其中会包含哪些材料并取得同意，用户不同意的材料不放入交接内容，即使交接内容将由用户本人复制粘贴

### Requirement: 结果回到对应位置
技能 SHALL 要求 Agent 把工作结果写回或关联到发起它的对象或位置，使用户能从同一处找到结果。无法自动取回时，MUST 说明结果在哪里以及如何手动带回。

#### Scenario: 继续同一工作得到新版本
- **WHEN** Agent 完成某份稿件的修改
- **THEN** 新版本出现在这份稿件的结果处，并保留与上一版本的关系，不出现在无关位置

#### Scenario: 结果无法自动取回
- **WHEN** 平台没有已核实的结果读取能力
- **THEN** 工作台在对应位置显示“结果在某个对话中，需要手动带回”，并提供带回的方法

### Requirement: 状态分开显示且不夸大
技能 SHALL 要求工作台把“已发送、已开始、已完成、待确认、失败”分开显示，每种状态 MUST 有对应证据：已发送表示交接已成功送达平台；已开始表示有证据显示 Agent 已开始处理；已完成表示 Agent 产出了结果；待确认表示结果或下一步需要用户决定；失败表示有明确失败证据。缺少证据时 MUST 保持上一个有证据的状态并标明无法确认最新情况，不得把已发送显示为已开始，或把已完成显示为用户已确认。

#### Scenario: 只能确认送达
- **WHEN** 平台只返回“消息已排队”，没有任何开始处理的证据
- **THEN** 工作台显示已发送，不显示已开始或进行中

#### Scenario: Agent 完成但需要用户决定
- **WHEN** Agent 生成了家长回复草稿，但发送应由用户本人决定
- **THEN** 工作台显示待确认，而不是已完成整件事

### Requirement: 外部影响动作每次单独确认
技能 SHALL 要求发送消息或邮件、提交或推送代码、付款、发布、删除、对外提交表单等产生外部影响的动作，每次执行前 MUST 取得用户针对这一次的明确确认。确认 MUST NOT 从历史习惯、已保存规则、之前的类似确认或工作台设计中推断。

#### Scenario: 历史中用户总是直接发送
- **WHEN** 历史显示用户以往收到草稿后都会直接发给客户
- **THEN** 工作台仍在每次发送前请用户确认，不提供自动发送

### Requirement: 分别核实平台四项能力
技能 SHALL 要求 Agent 针对用户当前使用的平台和环境，分别核实四项能力：读取历史、发起新工作、继续同一工作、取回结果。每项 MUST 记录为已核实、不支持或待核实，并写明核实方式；Agent MUST NOT 根据平台名称、宣传或其它用户的情况推断能力。待核实或不支持的能力 MUST 使用手动交接方式。

#### Scenario: 用户使用 Claude 或 WorkBuddy
- **WHEN** Agent 无法在当前环境中实际验证这些平台的接口
- **THEN** 四项能力都记为待核实，工作台对所有交接使用可复制内容并标明需手动完成

#### Scenario: 在 Codex 环境中已实际验证
- **WHEN** Agent 在用户的 Codex 环境中实际完成了一次发起和一次取回
- **THEN** 对应两项记为已核实并记录验证方式和版本，未验证的项仍记为待核实
