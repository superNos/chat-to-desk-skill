## Context

动机见 proposal.md 的 Why；行为契约见 `specs/` 下四个能力。本技能最早在一个多 Agent 开发总控技能的仓库中开发；本发布包只含新技能、评估材料、本变更文档和针对新技能的检查，不包含也不依赖那些技能。

新技能要服务的平台（Codex、Claude、WorkBuddy 等）能力各不相同，且本仓库无法逐一验证。技能的读者是“用户自己的 Agent”，最终受益者可能不是开发者。

## Goals / Non-Goals

**Goals:**

- 技能本身是一组方法、判断标准和记录格式，Agent 读完后能独立完成“确认范围 → 理解工作 → 用户校准 → 设计工作台 → 小范围试用 → 持续调整”的循环。
- 给出可检查的产物格式（工作模型、工作台说明），让用户和评估者都能追溯每项设计的依据。
- 提供足以做差异测试、反模板测试和使用测试的虚构材料与轻量自动校验。

**Non-Goals:**

- 不提供任何默认页面、组件库、看板或可直接安装的通用工作台。
- 不实现或声明任何第三方平台接口；平台适配只给核实方法。
- 不新增后台服务。
- 不读取真实用户对话作为样本。

## Decisions

### 1. 技能只交付方法与记录格式，不交付运行时

选择：`skills/personal-agent-workbench/` 只含 `SKILL.md`、`agents/openai.yaml` 和 `references/`，不含 `scripts/` 或 `assets/` 页面模板。

理由：任何内置页面都会变成事实上的默认模板，与“工作台由证据生成”冲突。Agent 本身有能力按设计写出本地文档、页面或平台内配置。替代方案“提供一个极简可配置页面骨架”被否决：即使字段可配，骨架的布局、状态栏和输入位置已经预设了工作形态；而且用户可能根本不需要页面。如后续真实使用证明某种无业务含义的运行支持（例如安全的本地文件读写约定）被反复重写，再另行提案。

### 2. 两类记录：工作模型与工作台说明

选择：工作模型记录授权范围、观察、证据、频率、校准状态和规则；工作台说明记录结论、元素、依据链、输入去向、结果位置、状态证据、单次确认动作、平台能力、试用范围和调整记录。格式写在 `references/` 中，作为结构建议而非字段强制，Markdown 即可。

理由：把“依据”从 Agent 的思考中拿出来写成用户可审阅的文字，是防止套模板最直接的手段，也让用户校准和后续调整有落点。替代方案“用 JSON Schema 强制字段”被否决：对非开发用户不可读，并会把字段名本身变成模板。

依据链约定：工作台元素 → 工作模型条目编号（已确认/已修正/已限定范围）→ 证据描述。评估时可机械检查链条是否断裂。

### 3. SKILL.md 保持短，按阶段路由到参考资料

选择：`SKILL.md` 只放循环、不可违反的边界（授权、单次确认、状态不夸大、无默认模板、允许不做工作台）和阶段到参考文件的路由。参考文件按阶段拆分：历史分析、校准访谈、设计原则、Agent 交互约定、平台适配、质量检查、案例。

理由：Agent 每个阶段只读需要的内容；案例单独放并标注“不可复制”，避免在设计阶段被当成模板读入。替代方案“把案例放进设计原则”被否决，因为最容易诱导照搬。

### 4. 案例与评估材料分开存放

选择：

- `skills/personal-agent-workbench/references/cases.md`：随技能安装，给 Agent 看“不同证据导致不同结论”的推理示范，含开发总控（得到一份开发任务台账）、非开发岗位和“暂不需要”结论。
- `evals/personal-agent-workbench/`：不随技能安装，含至少 3 组（实际 5 组）虚构用户历史、每组的期望判断要点、差异测试/反模板测试/使用测试的检查方法。

理由：评估材料包含“期望结论”，如果放进技能会让 Agent 对号入座。替代方案“只放一处”被否决。

### 5. 轻量自动校验只检查结构与边界，不检查文案措辞

选择：新增 `tests/test_personal_agent_workbench.py`（标准库 `unittest`），检查：

- 技能 frontmatter 有 `name`、`description`，`name` 与目录一致；`openai.yaml` 的 `default_prompt` 包含 `$personal-agent-workbench`。
- `SKILL.md` 路由到的参考文件都存在。
- 评估历史至少 3 组且至少一组标注为非开发岗位；每组期望结论中列出的元素都声明了来源证据编号，且该编号在本组历史中存在。
- 期望结论之间没有完全相同的元素集合；至少一组期望结论为“暂不需要复杂工作台”。
- 公开文件不含常见敏感模式（UUID、令牌前缀、私有绝对路径、内部域名）。

`scripts/check_skill.py` 检查：技能目录存在、调用名一致、README 提到技能、`SKILL.md` 路由到的参考文件存在。`scripts/release_check.py` 在发布前扫描敏感信息、图片元数据、隐藏文件和内部链接。

理由：语义质量（是否真按证据设计）无法用正则可靠判断，交给差异测试和独立复核；自动校验守住不会随措辞变化的结构不变量。

### 6. 安装方式

选择：README 给出手动复制命令；另提供只用标准库的 `scripts/install.py`，默认只预览要复制的文件，加 `--apply` 才复制，目标目录已存在时停止，不覆盖、不删除。

理由：技能只是一组文本文件，复制即可使用；预览优先、不覆盖，避免误伤用户已有的同名技能。其它 Agent 能否按这些文件工作没有验证，README 如实写明。

## Risks / Trade-offs

- [Agent 仍可能把案例当模板] → 案例文件开头和每个案例都写明不可复制；质量检查要求比对“元素是否来自本用户证据”；评估中加入反模板测试。
- [没有运行时，非开发用户得到的产物质量取决于 Agent 能力] → 允许并鼓励选择最轻的搭建形式（一段可复用说明、一份本地文档），并要求小范围试用后再加。
- [平台能力描述过时] → 平台适配只写核实方法和记录格式，不写任何平台“支持什么”的断言；Codex 部分也只写维护者在特定版本上用过的做法，作为可核实的线索，并要求在用户环境中重新核实。
- [历史分析触及隐私] → 三项授权分离、最小化保存、敏感类型只记类别、可删除；SECURITY 中补充说明。
- [自动校验被误解为质量证明] → README 与评估说明写明自动校验只覆盖结构，语义由差异测试和人工/独立复核判断。

## Migration Plan

纯新增。用户卸载时删除自己复制到技能目录下的 `personal-agent-workbench/` 即可；Agent 为用户生成的工作模型和工作台说明存放在用户选定的位置，由用户决定是否保留。不涉及用户数据迁移。
