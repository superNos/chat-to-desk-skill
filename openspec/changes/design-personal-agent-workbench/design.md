## Context

动机见 proposal.md 的 Why；行为契约见 `specs/` 下五个能力。本技能最早在一个多 Agent 开发总控技能的仓库中开发；本发布包只含新技能、评估材料、本变更文档和针对新技能的检查，不包含也不依赖那些技能。

新技能要服务的平台（Codex、Claude、WorkBuddy 等）能力各不相同，且本仓库无法逐一验证。技能的读者是“用户自己的 Agent”，最终受益者可能不是开发者。

## Goals / Non-Goals

**Goals:**

- 技能是一组方法、判断标准、记录格式和一个与工作内容无关的可选运行支持，Agent 读完后能独立完成“确认范围 → 理解工作 → 用户校准 → 设计工作台 → 小范围试用 → 持续调整”的循环。
- 给出可检查的产物格式（工作模型、工作台说明），让用户和评估者都能追溯每项设计的依据。
- 每位用户最终都能打开一个可交互的工作台，在里面完成“发起 → 看到状态 → 得到结果”。
- 提供足以做差异测试、反模板测试和使用测试的虚构材料与轻量自动校验。

**Non-Goals:**

- 不提供任何默认页面、组件库、看板或可直接安装的通用工作台；运行支持不含页面布局、职业字段或功能清单。
- 不声明任何未核实的第三方平台接口；Claude、WorkBuddy 等走复制交接，写“未验证”。
- 不提供远程或多人服务；运行支持只在本机环回地址上服务一位用户。
- 不读取真实用户对话作为样本。

## Decisions

### 1. 主要产出是可交互的本机工作台；技能附带与工作内容无关的运行支持

选择：技能的主要产出是一个用户在浏览器里打开的本机工作台，能发起新工作、继续某件工作、修改结果，并看到状态和结果。技能目录含 `SKILL.md`、`agents/openai.yaml`、`references/`，以及 `scripts/workbench.py`（只用 Python 标准库）和 `scripts/client.js`。运行支持负责提供页面、保存记录、交付适配和状态记录；页面和配置由 Agent 按该用户的工作台说明生成，放在用户指定的本机目录，不放进技能目录。技能目录不含任何页面、样式、图片或页面模板。

理由：v0.1.0 曾选择“不交付运行时，搭建形式可以只是一份文档”，理由是任何内置页面都会变成默认模板。用户看过两个演示后明确否定了这个方向：他要的是一个能操作的工作台，文档不能代替。修正后保留原来的顾虑，但把“不内置页面”和“不提供运行支持”分开：运行支持只处理与工作内容无关的事（本机服务、记录保存、交接、状态证据、安全），不决定页面上有什么，因此不会变成模板；而每个 Agent 都重写一遍本机服务和安全检查，既容易出错，也无法测试。

替代方案：

- “提供一个可配置的通用页面骨架”：仍被否决。即使字段可配，骨架的布局、栏目和输入位置已经预设了工作形态。
- “只给方法，让 Agent 每次自己写服务”：被否决。令牌、Host/Origin 检查、白名单和状态规则每次都要重写，质量无法保证，也无法自动测试。
- “最轻形式可以是一份文档”：被否决（用户明确不接受）。证据很少时给最小工作台，见决策 7。

### 2. 两类记录：工作模型与工作台说明

选择：工作模型记录授权范围、观察、证据、频率、校准状态和规则；工作台说明记录结论、元素、依据链、输入去向、结果位置、状态证据、单次确认动作、平台能力、试用范围和调整记录。格式写在 `references/` 中，作为结构建议而非字段强制，Markdown 即可。

理由：把“依据”从 Agent 的思考中拿出来写成用户可审阅的文字，是防止套模板最直接的手段，也让用户校准和后续调整有落点。替代方案“用 JSON Schema 强制字段”被否决：对非开发用户不可读，并会把字段名本身变成模板。

依据链约定：工作台元素 → 工作模型条目编号（已确认/已修正/已限定范围）→ 证据描述。评估时可机械检查链条是否断裂。

### 3. SKILL.md 保持短，按阶段路由到参考资料

选择：`SKILL.md` 只放循环、不可违反的边界（授权、单次确认、状态不夸大、无默认模板、主要产出是工作台）和阶段到参考文件的路由。参考文件按阶段拆分：历史分析、校准访谈、设计原则、Agent 交互约定、平台适配、运行支持、质量检查、调整、案例。

理由：Agent 每个阶段只读需要的内容；案例单独放并标注“不可复制”，避免在设计阶段被当成模板读入。替代方案“把案例放进设计原则”被否决，因为最容易诱导照搬。

### 4. 案例与评估材料分开存放

选择：

- `skills/personal-agent-workbench/references/cases.md`：随技能安装，给 Agent 看“不同证据导致不同结论”的推理示范，含开发总控（得到一份开发任务台账）、非开发岗位和“暂不需要”结论。
- `evals/personal-agent-workbench/`：不随技能安装，含至少 3 组（实际 5 组）虚构用户历史、每组的期望判断要点、差异测试/反模板测试/使用测试的检查方法。

理由：评估材料包含“期望结论”，如果放进技能会让 Agent 对号入座。替代方案“只放一处”被否决。

### 5. 轻量自动校验只检查结构与边界，不检查文案措辞

选择：新增 `tests/test_personal_agent_workbench.py`（标准库 `unittest`），检查：

- 技能 frontmatter 有 `name`、`description`，`name` 与目录一致；`openai.yaml` 的 `default_prompt` 包含 `$personal-agent-workbench`。
- `SKILL.md` 路由到的参考文件都存在。
- 评估历史至少 3 组且至少一组标注为非开发岗位；每组期望结论中列出的元素都声明了来源证据编号，且该编号在本组历史中存在。
- 期望结论之间没有完全相同的元素集合；至少一组期望结论为“暂不需要复杂工作台”，且它仍有不超过 2 个元素的最小工作台。
- 公开文件不含常见敏感模式（UUID、令牌前缀、私有绝对路径、内部域名）。

`scripts/check_skill.py` 检查：技能目录存在、调用名一致、README 提到技能、`SKILL.md` 路由到的参考文件存在；`scripts/` 只能有 `workbench.py` 与 `client.js`，技能目录不能有页面、样式或图片。`tests/test_workbench_runtime.py` 覆盖运行支持的令牌、Host/Origin、目标白名单、请求大小、私有文件、状态不夸大、手动交接和 Codex 适配器（用假的 app-server 会话）。`scripts/release_check.py` 在发布前扫描敏感信息、图片元数据、隐藏文件和内部链接。

理由：语义质量（是否真按证据设计）无法用正则可靠判断，交给差异测试和独立复核；自动校验守住不会随措辞变化的结构不变量。

### 6. 安装方式

选择：README 给出手动复制命令；另提供只用标准库的 `scripts/install.py`，默认只预览要复制的文件，加 `--apply` 才复制，目标目录已存在时停止，不覆盖、不删除。

理由：技能是一组文本文件和两个运行支持文件，复制即可使用，运行支持只需要 Python 3 标准库；预览优先、不覆盖，避免误伤用户已有的同名技能。其它 Agent 能否按这些文件工作没有验证，README 如实写明。

### 7. 证据很少时给最小工作台

选择：结论分三档：需要工作台、小工作台、暂不需要复杂工作台。第三档仍然搭一个工作台，只有一两个元素，通常是一个发起工作的输入框和一处找回结果的地方，之后按使用再调整。用户明确说不要时才停下。

理由：用户要的是工作台本身；功能少的工作台比一份文档更接近“通过工作台下发和取回”。保留“暂不需要复杂工作台”是为了防止证据不足时堆功能。

### 8. 状态只往前走，未知单独标记

选择：交接状态是“需手动完成 → 已发送 → 已开始 → 已完成”一条线，只往前走；“待确认”（结果已到、下一步要用户决定）和“失败”（有明确失败证据）单独显示。连接断开、超时、找不到这一轮时不改状态，另外标记“最新情况未知”。每次变化记录证据（来源和时间）。

理由：用户要求已发送、已开始、已完成、待确认、失败、无法确认分开显示且不夸大。把“未知”做成标记而不是一档，能同时保留上一个有证据的状态。

### 9. 交付适配：Codex 直接交付，其余复制交接

选择：配置里每个目标写 `adapter`（`manual` 或 `codex`）和三项能力的核实结果。只有 `adapter` 为 `codex` 且对应能力已核实时才直接交付或自动取回；其余一律生成交接文字，显示“需手动完成”，用户粘贴后点“已粘贴”，再把结果粘贴回原位置。Codex 适配器每次以参数列表方式启动本机 `codex app-server`（标准输入输出），对配置中的对话执行 `thread/resume`、`turn/start`，等待 `turn/completed` 后读取最后一条回复；`refresh` 用 `thread/read` 查询。Codex 发来的命令、改文件或权限请求一律拒绝，并提示用户到 Codex 里处理。

理由：Codex 的发送和取回在维护者环境中实际核实过（隔离的临时配置目录和只用于测试的临时对话，codex-cli 0.170.0）；Claude、WorkBuddy 没有核实，不能声称支持。拒绝审批请求是因为工作台不能替用户批准任何动作。

### 10. 本机安全边界

选择：只监听 127.0.0.1；Host 只接受本机地址；每次启动生成只在内存里的随机令牌，所有接口都要带；写操作要求同源 Origin，拒绝跨站请求；请求体 256 KB、单段文字 8000 字、单条记录 64 KB 上限；只提供 `page/` 下白名单后缀的文件，拒绝隐藏文件、路径穿越和指向目录以外的软链接，不提供配置和 `data/`；对话编号只从配置读，页面看不到也改不了；页面带内容安全策略，只能连接本机；状态文件权限为仅本人可读写；日志不记内容；不执行由用户输入拼出的命令。

理由：工作台里有用户的工作材料，本机端口可以被浏览器里其它网页访问，必须防跨站和 DNS 重绑定；交接目标如果能由页面指定，就可能被引到用户正在做别的事的对话。

## Risks / Trade-offs

- [Agent 仍可能把案例当模板] → 案例文件开头和每个案例都写明不可复制；质量检查要求比对“元素是否来自本用户证据”；评估中加入反模板测试。
- [页面质量取决于 Agent 能力] → 运行支持承担安全和状态规则；参考资料给出页面必须做到的事和交付前走查；首版只做一到三类工作，试用后再加。
- [运行支持被当成模板] → 它不含页面；`check_skill.py` 禁止技能目录出现页面、样式和图片；测试检查运行支持不含布局和职业字段。
- [本机服务被其它网页利用] → 决策 10 的令牌、Host/Origin、内容安全策略和目标白名单，均有自动测试。
- [Codex 接口变化] → 适配器只在核实过的能力上启用；接口异常时标“最新情况未知”而不是猜测；要求在用户环境里用 `codex-probe` 重新核实。
- [平台能力描述过时] → 平台适配只写核实方法和记录格式，不写任何平台“支持什么”的断言；Codex 部分也只写维护者在特定版本上用过的做法，作为可核实的线索，并要求在用户环境中重新核实。
- [历史分析触及隐私] → 三项授权分离、最小化保存、敏感类型只记类别、可删除；SECURITY 中补充说明。
- [自动校验被误解为质量证明] → README 与评估说明写明自动校验只覆盖结构，语义由差异测试和人工/独立复核判断。

## Migration Plan

纯新增。用户卸载时删除自己复制到技能目录下的 `personal-agent-workbench/` 即可；Agent 为用户生成的工作模型、工作台说明和工作台目录存放在用户选定的位置，由用户决定是否保留。v0.1.0 的用户如果得到的是文档，可以让 Agent 按 v0.2.0 把已确认的条目搭成工作台；已确认的条目不需要重新校准。
