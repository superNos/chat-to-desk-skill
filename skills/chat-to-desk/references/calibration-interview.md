# 用户校准访谈

目标：让用户用很少的力气纠正你的理解。校准结果是后续设计的唯一依据。

## 怎么展示发现

- 一次只展示最重要的 3 到 7 条，按“对用户影响大小”排序，不按你分析的顺序。
- 每条用用户的日常说法讲，并附一句证据，例如：“你给合唱团写排练通知，最近 4 周有 5 次都重新交代了‘先写集合时间，再写曲目’（3 月 2 日、3 月 9 日……）。”
- 推测要说成问题，例如：“我猜你有时找不到上次排好的声部名单，是这样吗？”
- 不要先给方案。先确认问题，再谈要不要做什么。

## 用户可以怎样回应

每条请用户选一种，也可以直接用自己的话说：

| 回应 | 你要做的 |
| --- | --- |
| 对 | 状态改为已确认 |
| 部分对 | 按用户说法改写，状态改为已修正 |
| 不对 / 以后不做了 | 状态改为已否定，后续不再引用 |
| 只在某种情况下 | 记下范围，状态改为已限定范围；之后只在这个范围内用它做设计依据 |
| 说不清 | 保持待校准，不用于设计 |

用户的“对”只确认你当时说出的那条发现，不确认你没讲、或只在追问里提到的细节。同一条里既有观察又有追问时，追问没得到回答，那部分细节仍是待校准或“历史未写明”。

## 校准工作方法，而非让用户设计页面

先用一件真实工作复述“什么触发 → 带什么材料 → 怎么处理 → 谁决定 → 得到什么”。再说明它在哪些独立事项中复用、哪些只是同一件事返工。只补问会改变工作流的缺口：步骤是否固定、每次变化什么、哪个结果可以交给下一步、什么时候算结束。不要要求用户自己列组件或编写流程提示词。

按日期呈现的记录须注明覆盖范围；“这些天看到了这种工作”与“你每天都会做”分开校准。已经明确确认的工作方法沿用，只核对矛盾和新增信息。

## 补问历史里看不到的事

历史只是用户工作的一部分。校准后补问几个具体问题，选用户关心的问：

- 有没有经常做、但不是在 Agent 对话里做的事？
- 哪件事最让你烦，或者最怕出错？
- 哪些结果最后要发给别人、交上去或付款？那一步通常谁来做？
- 有没有别人和你一起做这件事？他们能看到什么？
- 你现在怎么找回以前的结果？

用户补充的内容记为“用户自述”，同样经确认后才用于设计。

## 和非开发用户沟通

- 用工作里的词：通知、声部、学生、候选人、订单、回复、终稿；不说字段、接口、组件、状态机、页面结构。
- 举一个具体例子再问抽象问题。“下周要发排练通知时，你希望打开什么就能直接开始？”比“你需要哪些入口？”好答。
- 用户答不上来是正常的，说明这条还不重要，先放着。
- 不要用“效率提升”“智能化”这类说法推销工作台。用户说“现在这样就行”时，认真对待。
- 称呼用户时只用他自己给出的称呼；他没说姓名，就直接说“你”或“您”，不要编一个姓氏或名字。

## 校准结束时

用一小段话复述已确认的内容，以及你接下来打算怎么做，请用户确认。例如：

```text
确认一下：你主要的麻烦是每次写排练通知都要重讲格式、以及找不到上次的声部名单；问演出服租赁那次只是偶然。
接下来我只围绕这两件事想一个最小的做法给你看，你同意后再动手。
```

之前说过“确认之后再单独问你”的事（例如要不要长期记下某个格式），在这里一并问；即使你打算先不做它对应的东西，也要问，或者明确告诉用户推迟到什么时候再问。暂缓一项功能和暂缓询问授权是两件事。

如果已确认的条目里没有重复工作、没有跟进、也没有找结果困难，直接进入“工作台做多大”的判断（见 [workbench-design.md](workbench-design.md) 第 1 节），结论很可能是暂不需要复杂工作台，只做最小工作台。
