# 质量检查

交付草案、搭建试用版本、每次调整之前，逐项检查。任何一项不通过就先改，再给用户。

## 依据

- [ ] 每个元素都写了依据链，指向已确认、已修正或已限定范围的工作模型条目。
- [ ] 没有引用待校准、已否定或线索类条目。
- [ ] 写不出依据的想法放在“待确认建议”，没有进入试用版本。
- [ ] 工作台的大小与证据相称：证据少时只做了最小工作台（结论“暂不需要复杂工作台”），没有为了显得完整而加功能；也没有以“文档更轻”为由不做工作台。
- [ ] 交付物是一个能在浏览器里操作的工作台；Markdown 记录或交接文字只作为它的数据或导出内容。
- [ ] 在已有试用中查看一次真实结果。第一眼能读到结论及重要限制；可对照的数据带列标题、单位或日期口径，逐格与本轮输出一致；依据默认收起，展开可追溯。窄屏仍能读完整表格。
- [ ] 草案里能从用户要办的事说明为何选择本次 Skill、它解决了哪个决定，以及该决定如何进入功能或页面。已解决的环节可跳过；组件库的选择与落地按下面的组件体系检查。
- [ ] 设计草案里的布局已经体现在运行页面。用一条有代表性的记录检查：扫一眼能辨认当前对象、状态和主要按钮；切换或提交后，能在对应位置看见结果。在已有试用中顺手检查长文字、窄窗口和键盘焦点，通过即可。
- [ ] 工作台用附带的运行支持搭建（`workbench.json`、`page/`，页面通过 `/_workbench/client.js` 保存记录和交接）；没有用时，工作台说明写明用户的电脑为什么不能运行它、用户选了哪种做法。
- [ ] 搭建出来的试用版与用户确认的草案一致；需要改动（例如把“按人分组”改成一张表加一列）时，先说明理由并取得同意，再写进调整记录。

## 组件体系与中控台呈现

- [ ] 新建或整体改版已按设计指南选定成熟组件库/设计系统，记录选择依据与版本；依赖、实际源码引用及运行页面一致。只加一个样式表、图标包或安装但不使用，不能通过。局部调整只查受影响区域，未迁移的旧实现不宣称已达标。
- [ ] 页面中存在的核心列表/表格、按钮、输入/选择、弹层及状态反馈复用所选体系；业务区域有简短组件映射，主题、尺寸与图标一致，没有用另一套手写控件冒充组件库。
- [ ] 首屏可辨认当前对象、主要动作和最新结论。列表型工作没有被大表单、重复卡片与说明文案挤占；可比数据列对齐，重要限制可见，依据按需展开。组件库名称或默认主题不能代替实际视觉检查。
- [ ] 所选组件及字体、图标等资源从本机加载。适用时已执行必要的前端打包或启动检查，并在一条已有代表性记录中检查控件、长结果、窄屏及键盘操作；不为纯 UI 调整重跑 Agent 工作、外部操作或全量验收。环境例外如实记录，未验证的部分不宣称通过。

## 日常工作到功能的推导

- [ ] 覆盖范围与缺失历史已交代；按日记录使用有依据的工作时间，跨日事项未被拆散，空白日期没有被当作没工作或自动补日程。
- [ ] 能区分工作类别、具体事项、可复用流程与执行轮次；独立发生次数没有用对话数、消息数或返工次数代替。
- [ ] 每个常用功能均有触发、可变输入、稳定做法、产物及完成依据；多步骤明确交接、用户决定和停止点，不把聊天顺序推断成业务依赖。
- [ ] 草案能展示“工作证据 → 流程 → 功能 → 操作与结果”的关系；功能不是把对话摘要、聊天入口或提示词模板换个名称。
- [ ] 选一个已确认的成熟流程，正常路径无需打开聊天、重写完整指令、挑选执行对话或搬运中间结果。选择对象和必要参数后可直接执行，例外及新要求仍有合适的补充入口。
- [ ] 业务步骤与执行状态分开，产物回到对应步骤和版本；多步骤只在有证据时推进，失败或不确定时停在具体步骤，重试不重复已完成的外部动作。

## 完成与复用

- [ ] 当前事项逐条有范围内尚需处理的工作。已达到用户交付终点的事项退出当前列表，结果按授权保留可查；没有为此删除、归档平台对话或抹掉执行记录。全部办完时允许为空。
- [ ] 草稿交付、发布完成、待外部确认分别按用户要求判断。暂停、信息过期或结果未知没有被标成完成；已完成的子项不会掩盖尚未交付的部分，范围外建议不会变成新的待办。
- [ ] 每个常用按钮有不同独立事项实际使用同一做法的依据，或用户明确未来复用的声明。对话数、返工次数、主题相似和职业习惯均不单独构成依据。
- [ ] 用“同一件事聊了 20 次，已经交付且无未来复用需要”检查产出。它不在当前列表，也不会因此生成常用按钮；原结果仍可按原授权找回。
- [ ] 用“不同事项反复使用同一做法”和“只做过一次但明确以后还用”检查产出。具体完成事项退出当前列表，常用流程独立保留；再次运行使用新的对象或轮次，不覆盖旧结果或默认继承旧授权。连接未接通时入口禁用。

## 反模板

- [ ] 把元素名称换成另一位用户的工作，读起来是否就不成立？成立才说明它来自这位用户。
- [ ] 没有因为“工作台通常有”而出现任务卡、待办、看板、周报、统计图、仪表盘、优先级、截止日期、进度百分比；若出现，有证据和用户确认，且用的是用户的叫法。
- [ ] 页面的分区、先后顺序和叫法来自这位用户找东西、做事情的方式，不是某种常见后台页面的样子。
- [ ] 没有照搬 [cases.md](cases.md) 或其它用户的结构、字段和状态名。
- [ ] 非开发用户的工作台里没有任务编号、开发/复核/提交等开发流程词，除非用户自己这样说。
- [ ] 只有当用户的已确认工作是多 Agent 开发总控时，才提到开发任务台账一类的现成工具，且作为可选项。

## 交互约定

- [ ] 用授权历史中的零散问答做反例：只有咨询、没有后续工作时，页面不出现对应事项或常用按钮。一次提出的明确交付可以临时分派。
- [ ] 逐个检查业务功能，能说出它办完哪件事、产出什么，以及用户如何找回结果。只打开某段对话、填入一段提示词或显示对话摘要，不能单独算作已交付该功能。
- [ ] 存在符合复用条件的常用流程时，选一件有历史依据的事，能从事项直接运行该流程，无需先把模板填入编辑器再发送。
- [ ] 有临时分派需求时，打开输入框交代一次不同的工作；核对指令、执行去向和结果所属事项。若多段对话对应同一件事，从同一事项能找回相关执行记录。

- [ ] 每个输入都能说出去向：新工作、继续哪件事、修改哪个结果。
- [ ] 对未接通的目标，按钮和分派表单不可提交；尝试调用时服务端拒绝，既不创建执行记录也不发送指令。全程无须用户复制指令或粘贴回复。
- [ ] 从首屏用用户熟悉的业务动作完成一次已授权工作，核对实际目标收到的内容。可用且已授权的动作已接通，未接通的动作说明缺失环节。
- [ ] 有直接交付时，无需点刷新即可看到本轮实际产生的进度和最终结论。切换对象、继续下一轮或重新打开页面，仍能按对象和轮次找回结果；没有新证据时保留最后已知情况。
- [ ] 每类结果自动回到所属事项及轮次。中途断线保留最后证据，按原轮次恢复。
- [ ] 状态只用有证据的那一档，没有把已发送写成已开始、把草稿完成写成事情办完；没拿到结果没有写成失败。
- [ ] 发送、提交、付款、发布、删除、对外提交表单等动作，每次都需要用户自己确认，没有任何自动执行。
- [ ] 页面上能看到授权边界：哪些材料会交出去、哪些不会，哪些能力还没核实。
- [ ] 交给用户前，在页面里用一条用户同意的试用内容走过一遍“发起 → 看到状态 → 得到结果”，关掉再打开记录还在。

## 执行项目归属（适用时）

- [ ] 流程绑定可追溯到用户明确选择或同类工作的项目记录。用两个项目共用目录的例子检查，新建、重试和续办均能落到选定项目。以宿主返回的对话归属验收。
- [ ] 目标项目失效或返回归属不符时，业务指令停在发送之前。若用户要求移动既有对话，按指定对话逐条核对迁移结果。

## 只读联网与按编号查询（适用时）

- [ ] 用一个已授权事项，从页面触发真实只读查询。核对实际轮次生效的文件只读策略、目标来源的读取结果，以及结论自动回到同一事项和轮次。仅收到 Agent 回复或连通测试成功时，业务读取仍待验证。
- [ ] 在代表性试用或虚构样例中选择默认列表以外的事项，检查完整编号、所属范围、来源返回的内部 ID（如需）与最终详情一致。近似编号和其他范围的同号记录都不会被选中。
- [ ] 检查受阻结果能区分网络不可达、无读取权限、查无匹配和多条匹配。修复后沿原事项新建轮次，保留先前结果。可用隔离样例核对异常分支，真实查询复用同一次试用。

## 事项续办与可处理的失败

- [ ] 用同一件事的失败、重试成功和补充安排检查：它们在同一事项下，原轮次及结果保留；另一批独立工作单独建事项。事项摘要不再把旧结果写成“最近一次”。
- [ ] 有临时安排需求时，当前列表为空也能发起工作；输入可以归到新事项或已有事项，不强迫选择对话，不自动生成常用按钮。缺少归属信息时不会猜测关联。
- [ ] 对已知失效的连接或凭据，只做必要检查并显示具体处理入口，未通过前不启动完整 Agent 流程。更新凭据使用本机安全输入与存储，失败不泄露输入、不覆盖此前有效凭据。
- [ ] 失败处理后的重试沿用原事项并新建执行轮次。用户关闭再打开页面，仍能找到事项及其各轮结果；连接验证与实际业务执行分别展示结果。

## 授权与隐私

- [ ] 只读了授权范围内的来源，排除项都已跳过。
- [ ] 用户说“说不清”的授权项（例如保存多久），在回复和记录里都写成待定，没有替用户选更宽的做法。
- [ ] 分析、保存规则、交给 Agent 三项授权分别取得。
- [ ] 未同意“保存发现”时，没有把观察和证据写成文件；未同意“保存规则”时，持久记录里的规则和背景资料只有编号和“待问”，没有原文。
- [ ] 交接内容里的材料都在“交给 Agent 执行”的授权范围内，包括由用户自己复制粘贴的交接内容，也包括“背景”一栏预填的身份、单位等信息。
- [ ] 对用户说过“会先做”的步骤（例如先给你看分类再细读）都做了；改了做法的，事先告诉了用户并取得同意。
- [ ] 说过“之后再单独问你”的授权或问题（例如要不要保存某个格式），在本阶段结束前问了；决定不问或推迟时，告诉了用户并写明什么时候再问。
- [ ] 观察里没有历史未写明的细节；用户只答“对”的条目，没有把追问里未回答的部分当作已确认。
- [ ] 工作模型和工作台说明里没有密码、令牌、账号、证件、付款信息、第三方个人敏感信息或大段原文。
- [ ] 存放位置是用户指定的本机位置，没有放到会公开或同步给他人的地方。
- [ ] 工作台只在本机访问，页面没有引用外部地址（`workbench.py check` 通过），不把内容发到外部服务；页面、配置和数据都不在技能目录里。
- [ ] 用了 Codex 适配器时，目标对话是用户专门同意的那几个，对应能力在用户环境里核实过。

## 易懂

- [ ] 第一次使用的用户读完草案，能说出这东西帮他做哪两三件事、怎么开始用。
- [ ] 不熟悉技术的用户不需要理解字段、接口、页面结构也能确认或否定设计。
- [ ] 用户可以随时说“先不要”；不熟悉命令行的用户不需要自己启动服务，工作台说明写清了下次怎么打开。
- [ ] 工作台说明包含 [workbench-design.md](workbench-design.md) 第 6 节列出的各节（结论、页面上有什么、输入去哪里、结果回到哪里、状态怎么显示、每次都要你确认的动作、平台能力、怎么打开、试用范围、待确认建议、调整记录），标题可以换成用户的说法；某节暂时没有内容就写“暂无”，不要省掉。
- [ ] 称呼用户只用他自己给出的称呼，没有编造姓名。
