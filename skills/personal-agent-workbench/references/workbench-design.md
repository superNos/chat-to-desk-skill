# 工作台设计原则

目标：为用户做一个在他电脑上用浏览器打开、可以操作的工作台。里面放什么，只由他已确认的工作决定，每个元素都说得出依据；能做小就做小。

## 1. 工作台是主要产出

本技能交付的是一个可交互的本机工作台：用户在里面能发起新工作、继续某件工作、修改某个结果，并看到每件事的状态和 Agent 返回的结果。Markdown 记录、交接文字、导出的表格只能作为工作台里的数据或导出内容，不能代替工作台。

工作台的大小按证据定，不是“做或不做”：

| 大小 | 什么时候 | 里面大致有什么 |
| --- | --- | --- |
| 最小工作台 | 已确认的条目里看不到重复工作、跟进或找结果困难，或者历史太少 | 一个发起工作的入口，加一处找回这些工作结果的地方。结论写“暂不需要复杂工作台” |
| 小工作台 | 有一两件反复做的事，例如每次重讲背景、按某个对象找回结果 | 围绕这一两件事的入口、对象和结果查看 |
| 需要工作台（功能较多） | 同时有好几件事在进行、需要知道各自到了哪一步，或要在一处下发和取回多件事 | 按用户的工作对象组织的区域、状态和各自的输入 |

“暂不需要复杂工作台”的意思是功能少，不是不做工作台。告诉用户依据，并用他的工作说明什么情况下值得加东西（例如“如果之后你开始隔几天回来接着改同一件事”）。

用户可以随时说“先不要”。他不想要任何工作台时，照他的意思停下，在工作台说明的结论里写“用户决定暂不搭建”和他的原话；不要因为“写个文档更轻”而主动替他做这个决定。

## 2. 从工作推导元素，不从模板推导

先按 [workflow-abstraction.md](workflow-abstraction.md) 还原并校准流程，将触发、参数、步骤、用户决定和产物映射为功能。按工作类别、对象关系及操作顺序组织首屏，不按对话标题、消息时间线或 Agent 名称划分。已确认的流程与产物是设计输入，不能从一张对话摘要列表直接跳到界面。

对每个已确认流程或一次性事项问：用户在这件事里需要 **输入什么、看到什么、找回什么、决定什么**？答案就是候选元素。元素可以是：

- 输入：开始一件新工作的入口、对某个结果的修改意见、补充背景；
- 对象：用户工作里的“东西”，用用户的叫法（某位客户的稿件、某个班的家长消息、某个候选人）；
- 对象上的信息：只放用户在历史里真的会看、会问、会用来判断的内容；
- 状态：这件事交出去之后到了哪一步，按 [agent-interaction.md](agent-interaction.md) 第 4 节的证据显示；
- 结果查看：按用户找东西的方式组织（按客户、按日期、按学生）；
- 确认：需要用户拍板的那一步，由用户自己完成；
- 背景资料：反复说明的要求，保存一次、按需带上（需要“保存规则”这项授权）。没有这项授权时，它仍可以作为元素：你只在当前对话里给出全文，由用户自己留存、每次自己带上；工作台和持久记录里只写编号和“待问”，不写原文。

不要从“一个工作台通常有什么”出发。任务卡、待办、看板、周报、统计图、仪表盘、优先级、截止日期、标签、进度百分比都不是默认元素；只有证据显示用户确实需要并经确认，才放进来，并改用用户的叫法。页面的布局、分区和先后顺序同样从用户找东西、做事情的顺序推出来，不要套用某种常见的后台页面或其它用户的页面。

每加一个元素，在依据附录里记一行：元素、对应的工作模型条目编号及确认状态。写不出依据的元素删掉；你仍认为有价值的，放进“待确认建议”，写明缺什么证据。

最小工作台的两样东西（发起入口、找回结果的地方）的依据，是用户这次请你帮他整理工作的诉求和已确认的条目，在说明里如实写成“用户这次的诉求（用户自述）”。除此之外的元素仍然要有各自的证据。

### 从一件事安排工作

按用户要达成的结果识别事项。几段对话可能分别涉及同一件事的准备、执行和核验，一段对话也可能谈到几件独立的事。只有证据支持时才归并。给事项一个稳定标识；每次执行另记流程、去向和轮次，便于切换执行对话后仍能找回这件事的结果。来源对话按需展开。

- **常用流程**。先按 [历史分析](history-analysis.md) 确认有跨独立事项复用或用户明确未来复用的依据，再由历史和校准明确何时做、按哪些步骤做、交给谁以及要拿回什么时，用用户熟悉的动作命名按钮。点击即为本次对象创建新的事项或执行轮次，执行已授权步骤，保留旧结果。已完成的实例退出当前列表，流程可以独立保留。只有本次会变化的必要参数才请用户选择；涉及外部影响仍在相应步骤确认。待接通的动作显示原因并禁用。
- **流程功能**。常用按钮只是入口之一。流程需要选择范围、导入材料、逐项核对或编辑产物时，将必要操作组织成专用表单、列表或编辑区。正常路径由业务操作推进，固定规则自动带入；自由输入不承担重复描述已知工作方法的职责。
- **临时分派**。当用户需要为这件事交代一次具体安排时，再打开输入框或对话框。在里面写要求，选择或核对执行去向；发出后在原事项跟进结果。临时指令单独下发，不自动附带某个常用流程的步骤。只有当用户确有这类工作时才设置该入口。

### 把事情、流程和执行轮次分开

事项代表用户的一次交付目标，常用流程代表可复用的做法，每次执行是该事项下面的一轮记录。失败后的重试、补充材料和修改结果仍归到原事项；新的对象、批次或交付目标才新建事项。分别保留每轮原结果，事项摘要使用最新有效结论，并标明时间与未完成部分。不能将所有执行轮次平铺成事项，也不能因共用一个流程把不同交付目标全部合并。

有临时安排需求时，即使当前列表为空，用户仍能发起新工作。输入后可根据已有事项给出归属建议，只有确定对应关系时才自动关联；不确定或存在多个对象时，让用户选择“新建”或具体已有事项。不要要求用户先挑 Agent 对话。一段临时安排不会自动成为常用按钮，执行目标与权限仍按已核实的能力和本次授权确定。

已有流程因连接、凭据或输入问题失败时，把可操作的下一步放在对应事项旁；重试创建新轮次，不覆盖失败记录。只有真实失败过的前置条件才加检查入口。需要凭据时，使用宿主的安全凭据存储和本机密码输入，不让非开发用户修改源码、规范文件或把密钥粘进聊天。凭据不得进入工作记录、提示词或公开仓库，连接检查成功也不能冒充工作已完成。

以上是按实际需求采用的行为要求，不是所有用户都要有的固定栏目。已有一件简单工作的工作台无需增加流程管理或设置中心。

## 3. 每个工作台都要满足的交互约定

### 把规划、产品设计和前端设计用在不同决策上

按[协作 Skill 选择指南](skill-selection.md)解决当前事项尚未确定的设计问题。把选出的功能、触发动作、结果去向和完成条件交给前端设计，并入同一份草案。

### 成熟组件库是实现基线

新建工作台或整体重做 UI 时，必须选定并实际使用一套成熟组件库或宿主已有的成熟设计系统。不能默认用原生控件加手写 CSS 搭整套中控台，也不能只引入表格样式、图标包、CSS 工具类或无样式交互基础件就宣称满足要求。语义化 HTML 仍用于正文和布局，自定义代码负责用户专属的工作流与组件组合。

按下面顺序选择，由 Agent 核对环境并决定，不把技术选型转交给非开发用户：

| 环境 | 选择与约束 |
| --- | --- |
| 已有应用或已建立组件体系的工作台 | 先复用其成熟组件、主题和图标体系，避免混搭第二套基础控件；用户明确要求替换时再迁移 |
| 新建且没有既有前端约束的中控台 | 默认采用 React + Ant Design，利用其表格、输入、弹层及统一主题配置；按实际工作组合，不套用整套后台模板 |
| 已有 Vue 3 技术栈 | 优先 Element Plus；已有其他成熟设计系统且满足需求时沿用 |
| 宿主有固定渲染方式，或没有 Node、不能联网安装依赖 | 先找可在该环境运行的成熟组件方案，例如随包附带的预编译组件库静态文件；确实不可行时告诉用户具体限制，不静默退回手写控件并宣称达标 |

用户明确指定的库或实现约束优先；有例外就在现有工作台说明里记录原因与实际采用的方案，不新增一轮例行审批。局部修正文案或样式时不借此迁移整个旧页面；整体改版时将未采用组件体系的部分纳入已授权的 UI 范围，未完成前如实标明。

安装依赖沿用工作台搭建授权，在指定本机目录管理；需要系统级安装或超出授权的外部服务时才另问。实现前查所选库的官方文档及与宿主兼容的版本，固定依赖与锁文件。只带需要的组件与资源，保留许可证，运行时从本机加载，不依赖远程 CDN、字体或统计服务。可从 [Ant Design 主题文档](https://ant.design/docs/react/customize-theme/) 和 [Element Plus 全局配置](https://element-plus.org/en-US/component/config-provider.html) 核对其支持的主题与尺寸设置；具体 API 以实际安装版本为准。

所选库和版本记在依据附录里。以库支持的主题变量、尺寸配置和图标系统统一视觉，不靠大量 CSS 覆盖把组件重画一遍。

### 组件库之上的中控台排版

组件库保证基础控件一致，产品设计决定用户如何办事。`frontend-design` 等视觉技能必须在所选组件体系内完成信息层级、密度和真实结果设计，不能另造一套平行控件。

- 工作以逐项选择、比较、处理为主时，优先紧凑列表或表格配合操作栏、行内按钮与详情区；编辑文稿等工作仍以产物编辑区为主。统一组件质量，不统一所有用户的布局。
- 常用动作靠近当前对象，必要参数在紧凑操作区；低频设置和较长输入按需放入抽屉或弹窗。输入本身不是主要工作时，不让大表单占据首屏。
- 优先采用组件库的标准或紧凑密度、字体层级与间距。保留长文字可读性、点击区域、键盘焦点和窄屏使用，不靠把文字缩得很小来制造紧凑感。
- 结果区先给结论和重要限制，再给对照表；依据与过程按需展开。避免重复标题、介绍文案、大块留白、重复套卡片或给每个字段单独造卡片。
- 不添加装饰性 KPI、欢迎横幅、渐变大背景、聊天气泡、表情图标或无依据的进度数字。库自带的这些组件并不构成使用它们的业务依据。
- 首屏只回答三件事：现在要处理哪些事、下一步点什么、最新结论是什么。平台能力、授权说明、执行编号、对话名称和历次执行都不上首屏。

### 用真实返回结果设计结果区

先问用户拿到结果要作什么判断。把本轮已有结论写成第一眼能读懂的一句话，保留限定条件和不确定性。涉及多个对象或方案的同类数据时用带列标题的语义化表格，统一单位和日期格式，按同一口径对齐；只有一条简短回复时用正文即可。支撑结论的文件位置、数据口径或详细推导默认折叠，入口说明展开后能看什么。影响用户判断的限制（如仅核对源码，尚未实测）与结论一起可见。

用该事项本轮的真实返回值填充这些位置，保留原文供追溯。字段缺失时如实展示，不能从摘要猜测数值。如无法可靠识别结构，就保留可读原文。渲染 Agent 文本时只生成允许的界面元素，用户内容作为纯文本处理。

**在工作台草案里落实视觉设计。** 给设计技能的简报只需概括已确认的工作对象、使用频率、主要动作和用户提供的视觉参考，示例使用虚构或脱敏内容。把排版决定合入已有草案：首屏焦点、列表或编辑区如何排列、主要按钮在哪里、正常与待处理状态怎样区分。已有工具风格或用户指定的中控台可作为视觉参照。工作对象与操作仍按这位用户的工作确定；引入其它服务或传输材料须遵守原有授权。

首屏先放这位用户最常做的业务动作，用他自己的动词命名，旁边放选择对象和判断下一步所需的信息。对话编号、连接设置和查询细节按需展开。如果用户平时逐项比较再处理，可以用列表选择对象，在行内或详情区执行动作；如果他围绕一份稿件反复修改，就让稿件和修改入口占主要位置。用有边界的按钮区分主操作与辅助操作，清楚标出当前行，把结果留在对应记录的详情区。交接原文、状态历史和低频表单按需展开。列表适合阅读消息，列对齐的台账适合比较查询；根据用户实际工作选择。用明确的标题层级、统一的间距、可辨认的状态文字和可见的键盘焦点建立视觉秩序。

把视觉检查并入原有试用：用一条有代表性的记录走完主要操作，顺手缩窄窗口、用键盘定位输入，看看能否找到对象、下一步和结果，文字是否挡住操作。通过即停止；发现问题只复查受影响的地方，不为换配色重跑访谈或生成整套演示。

下面是约定，不是布局。具体放在哪、叫什么，由这位用户的工作决定：

- 每个输入在交出前都有明确去向：新工作、继续哪件事、修改哪个结果（见 [agent-interaction.md](agent-interaction.md) 第 1 节）。
- 启用的按钮和临时分派表单必须直接驱动 Agent，自动取回进度与结果。未接通时禁用对应动作并说明原因。
- 结果回到发起它的那件事或那个对象旁边。
- 状态按 [runtime.md](runtime.md) 第 5 节的用户说法显示，证据按需展开。
- 有外部影响的动作按 [agent-interaction.md](agent-interaction.md) 第 5 节处理。
- 交出的材料可以在发送区用一行默认折叠的“会交出：……”说明；能力核实情况写在依据附录，页面上只把未接通的动作禁用并说明原因。

## 4. 搭建方式

用本技能附带的运行支持搭建：你按工作台说明生成这位用户的页面和配置，放在用户指定的本机目录里，由运行支持在本机打开。动手前先读 [runtime.md](runtime.md)，里面有目录结构、配置格式、页面要做到的事和安全要求。运行支持不带任何页面，页面每一处都由你为这位用户写；它负责保存记录、生成交接内容、记录状态证据，你不需要在页面里自己实现这些。

不要把页面、配置或用户数据放进技能目录，也不要放进会公开或同步给他人的位置，除非用户明确要求。

本机无法运行附带服务时，可接入用户平台上已核实的等效执行与回传接口。若仍无法直接控制 Agent，向用户说明缺失能力和当前交付状态。

用户已经在用某个工具（表格、笔记、文件夹）存放工作时，工作台可以链接到那里，或者提供导出给那个工具的内容；不要另起一套重复记录，也不要把导出内容当成工作台本身。

不熟悉命令行的用户，不要让他自己维护服务：由你启动；在工作台说明里用一两句话写清下次怎么打开、打不开时怎么办。

## 5. 先给草案，再搭建

搭建前给用户看一份草案，只有两样：

- 一张页面草图（几行文字或线框都可以），标出首屏有哪几块、各自对应哪件已确认的事；
- 一件真实事项的点击路径：选什么、点什么、在哪里看到结果和作决定。顺带一句哪些事由他本人完成。

草案里，每件已确认的麻烦都要么给出对应的做法，要么写明暂缓及理由；不要把“要不要为这件已确认的事加一样东西”留成开放问题。用户可以在草案上删、改或说“先不要”。用户对草案里某一项说“说不清”或“按你的建议”时，由你按影响大小给出建议并说明理由，再请他确认。

用户确认后再搭。首个版本只覆盖用户选定的一到三类工作。用户想一次全做时，先说明理由：先试最重要的几件，能更快看出哪些真有用，少做以后要拆掉的东西；用户仍坚持时，按用户决定执行，并在工作台说明中记录。

搭好后按 [quality-checks.md](quality-checks.md) 用一条用户同意的试用内容走一遍，再请用户自己试。

## 6. 使用说明和依据附录

和工作台放在一起的有两份文件。

**使用说明**给用户看，只有四节，用他的叫法写，没有内容的写“暂无”：

```markdown
# 婚礼供应商工作台（版本 1，2026-05-16）

## 能做什么
按新人分开看供应商回复；选一家供应商点“起草询价”，草稿自动回到这家下面。

## 怎么打开
我已经帮你打开了。下次把这句话发给我：“打开我的婚礼供应商工作台”。

## 由你本人完成
把方案发给新人；给供应商付定金。

## 待确认建议
预算超支提醒：等超支真的发生过再加。
```
