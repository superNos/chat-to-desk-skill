# 按用户要办的事选择协作 Skill

校准工作观察时，先找出会影响目标或授权的歧义；用户确认后，再为首版取舍和产品设计选择技能。每次先写清这件事从什么开始、最终要拿到什么，以及还缺哪一个决定。已有工作台只做局部调整时，从发生变化的那一步开始。

| 什么时候用 | 优先匹配的 Skill | 带入什么，拿回什么 | 什么时候跳过 |
| --- | --- | --- | --- |
| 用户确定有困扰，但同一段工作有几种不同解释，例如到底要“起草”还是“代发” | 需求探索类，如环境中的 `openspec-explore` | 用用户原话和已有约束列出会改变方案的差异，只校准关键问题。该 Skill 用于思考；进入实现时切回搭建流程 | 对象、目标和边界已经确认 |
| 校准后有多个值得做的候选，首版需要取舍 | `prioritize-features` | 比较实际复用、返工、能节省的操作、接入成本和不确定性。产出首版要做什么、什么暂缓及理由 | 用户已经选定事项，或只剩一个明确动作 |
| 一件事跨人、跨工具、跨阶段，容易漏掉交接或找不到结果 | 新流程可用 `customer-journey-map`；有现有页面和改版目标时，可用环境中的 `requirement-walkthrough` | 用一件真实工作还原“谁开始、在哪里交接、谁确认、结果回哪里”。给界面设计留下主操作、等待状态和恢复入口 | 一步可办完，或现有路径已经核实且本次不变 |
| 事项已选，用户与 Agent 的责任或“什么算办完”还不清楚 | `user-stories` | 将已确认的目标收敛成可观察的完成条件。例如“草稿已返回”和“用户已发出”要有各自的依据 | 已有明确的输入、去向、结果和完成证据 |
| 行为已定，要把控件或真实结果做成可操作的界面 | `frontend-design` 或宿主可用的同类技能 | 带入已选事项、用户动作、真实结果的脱敏结构和使用环境，决定信息层级、组件和排版 | 这次只梳理工作，没有界面变化 |

## Agent 如何主动选择

1. 查看宿主当前提供的技能名称和说明。按表中的决策找候选，读取匹配项的 `SKILL.md`，核对适用条件、依赖和实际产出后使用。名称相同但产出不合适时，继续找等效能力。无需用户逐个点名。
2. 同一决策有多个可用技能时，优先用能利用现有证据、最少重复工作的那个。一个决策解决后再判断下一处缺口；只把决定、已确认约束和必要的脱敏材料传给下一步。用户的取舍、授权及真实证据优先，不为配合模板补功能、凑数量或猜评分。
3. 公共候选 `prioritize-features`、`customer-journey-map`、`user-stories` 可在上游仓库 `phuryn/pm-skills` 核对，分别属于 `pm-product-discovery`、`pm-market-research`、`pm-execution`。这些是能力示例。当前宿主未提供时，优先用已安装的同类技能或本技能的访谈、设计指南继续；用户希望扩充能力时再用 `find-skills` 查找。安装新技能和向外部服务提供材料分别遵循用户授权。
4. 在已有草案里用一句话记下这次的选择和产出，例如“先梳理询价交接，确定回复归供应商；再设计行内续问和待确认状态”。没有调用外部技能时，如实写明采用的本地方法。

## 三个不同的选择

- **店铺售后首版**。已确认退货核对、补发登记和月底汇总都需要做，但用户想先试一件。用功能取舍技能比较已有的返工与接入证据，给出首选及理由；用户指定先做补发后，直接围绕补发设计。
- **活动询价**。用户已确定要跟进供应商，困难在于报价、改稿和最终确认散落在不同对话。跳过优先级排序，用旅程梳理找到接续和拍板的节点，再做界面。若谁来确认也已明确，就跳过用户故事这一步。
- **已有筛选核对按钮，只改结果呈现**。沿用已确认的目标和验收口径，直接用前端设计把本轮结果排成结论、日期对照表和可展开的依据。一次问完就结束、也没有交付需求的咨询，继续留在历史中。
