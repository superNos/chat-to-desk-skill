# 本机运行支持（可选）

目标：让你为用户生成的工作台页面能在他电脑上打开、保存记录、把交接交给 Agent 或生成可复制内容，并如实显示状态。运行支持只做这些与工作内容无关的事。

它在技能目录的 `scripts/` 下：`workbench.py`（只用 Python 3 标准库）和 `client.js`（页面可选用的接口封装）。它们不含任何页面、栏目、职业字段或功能清单。页面和配置都由你按这位用户的工作台说明生成。

## 1. 工作台目录

放在用户指定的本机目录，不放进技能目录，也不放进会公开或同步给他人的位置：

```text
<工作台目录>/
  workbench.json   交付目标和平台能力，由你生成
  page/            这位用户的页面，由你生成；首页是 page/index.html，可以拆成多个文件
  data/            运行支持自动创建，只有本人可读：state.json 存页面记录和交接记录
```

运行支持只对外提供 `page/` 里的页面文件（html、css、js、svg 和常见图片）和 `/_workbench/client.js`。`workbench.json`、`data/`、隐藏文件和其它任何文件都不提供。

## 2. 配置 workbench.json

配置只写交付目标，不写页面内容。下面的尖括号是占位，按用户的情况填：

```json
{
  "title": "<给用户看的工作台名称>",
  "targets": {
    "<目标名>": {
      "label": "<给用户看的名称，例如他平时处理这类事的那个对话>",
      "platform": "<平台名称与版本，没核实就写待核实>",
      "adapter": "manual",
      "capabilities": {"发起工作": "待核实", "继续同一工作": "待核实", "取回结果": "待核实"}
    }
  }
}
```

- `targets`：可以交接到哪里。只有这里列出的目标能用；页面不能另外指定对话。只配置用户确认过的目标。
- `adapter`：`manual`（复制交接，默认）或 `codex`（直接交给 Codex 对话，见第 6 节）。
- `capabilities`：照抄工作台说明“平台能力”一节的结果，只能以“已核实”“不支持”“待核实”开头。运行支持只在 `adapter` 为 `codex` 且对应能力“已核实”时才直接交付或自动取回，其余一律走复制交接。
- `labels`（可选）：交接内容的四个标签可以换成用户的说法，键只能是 `destination`、`background`、`ask`、`expect`。
- `codex_turn_minutes`（可选）：等 Codex 这一轮结束最多多少分钟，默认 60。

写好后运行检查：

```bash
python3 <技能目录>/scripts/workbench.py check --dir <工作台目录>
```

它检查配置、首页是否存在、页面有没有引用外部地址。页面只能用本机资源，不要引用外部字体、脚本、图片或统计服务。

## 3. 打开工作台

```bash
python3 <技能目录>/scripts/workbench.py serve --dir <工作台目录> --open
```

它只监听 127.0.0.1，从 48760 开始找空闲端口，启动时打印地址。关掉这个进程，工作台就关了；记录留在 `data/` 里，下次打开还在。

在你的环境能启动它时由你启动，并告诉用户地址。你的环境不允许监听端口时，仍然照这一节搭好，给用户一行可以直接复制的命令，并说明打开后在浏览器里看到什么、第 7 节的试用怎么走；不要因此改成单个离线页面或文档。在工作台说明的“怎么打开”一节写清下次怎么打开。

## 4. 页面怎么和运行支持通信

页面里引入：

```html
<script src="/_workbench/client.js"></script>
```

之后用 `window.Workbench` 上的方法。页面的布局、文案、按钮放在哪里，全部由你按工作台说明决定。

| 方法 | 做什么 |
| --- | --- |
| `state()` | 读取目标（不含对话编号）、交接标签、页面记录和全部交接记录 |
| `saveRecord(key, value)` | 新建页面自己的一条记录，例如用户录入的一个工作对象。内容由页面决定，单条不超过 64 KB。这个记录名已经存在时会被拒绝，不会悄悄覆盖 |
| `replaceRecord(key, value, true)`、`deleteRecord(key, true)` | 覆盖或删除一条记录。页面必须先请用户确认这一次，确认后才传 `true` |
| `handoff({...})` | 发起一次交接，见下表 |
| `markPasted(id)` | 用户把交接内容粘贴到对话后自己点的 |
| `addResult(id, text)` | 用户把对话里的结果粘贴回来 |
| `markDone(id, note)` | 待确认的事由用户自己处理完后记一笔，例如“我已自己发出” |
| `markFailed(id, reason)` | 用户看到了明确的失败信息 |
| `refresh(id)` | 直接交给 Codex 的交接，重新查一次最新情况 |
| `statusText(handoff)`、`copyText(text)` | 状态的标准写法；复制文字 |

`handoff` 的参数：

| 参数 | 说明 |
| --- | --- |
| `target` | 配置里的目标名 |
| `intent` | `new`（新工作）、`continue`（继续某件事）、`revise`（修改结果）。必须由用户选或由输入框所在位置决定，不能猜 |
| `about` | 继续或修改的是哪一件，用用户的说法写，例如“S07 家长 3 月 11 日的消息的回复草稿” |
| `ref` | 页面自己的对象编号，用来把这次交接和结果挂回对应对象 |
| `background`、`ask`、`expect` | 背景、这次要做、完成后给我。背景里只放已授权交出的材料 |
| `confirmAfter` | 结果出来后还要用户拍板（例如由他本人发出）时为 `true`，拿到结果后显示待确认 |
| `continues` | 这次是接着哪一条交接，例如修改上一版的结果 |

运行支持按这些内容生成交接文字。每条交接记录里有：`status`（状态）、`unknown`（最新情况是否未知）、`text`（交接内容）、`direct`（是否已直接交给 Agent）、`results`（结果，带来源和先后编号）、`events`（每次状态变化及证据）、`note`（需要用户知道的提示）。

### 打开、同步和找回结果

- 打开或重新打开页面时立即调用 `state()`，按工作对象 `ref` 和交接 `id` 恢复记录。同一对象的每次继续或修改都有自己的交接，用 `continues` 找上一轮。展示当前轮次最新一版 `results`；当前轮还在工作时，可以标出“上一轮结论”供查阅。迟到的旧轮回复只更新它所属的记录。
- 直接交付后，在页面可见且有工作进行时隔几秒读一次 `state()`，上一次读取结束再安排下一次。恢复可见时立即读取；只更新对应记录，保留选中对象、焦点和未提交输入。后台等待负责接收事件。重开时对仍未结束且有 `delivery.turn` 的直接交接，可用 `refresh(id)` 按原轮次补查，再读状态。本服务仍在监听这条交接时，刷新直接使用原会话的实时更新。监听退出或服务重启后，刷新才按编号查询原轮次。补查不会重新发送工作。
- Codex 完整发出一条过程说明后，本机记录会有可选的 `progress = {text, time}`，只保留本轮最新一条及接收时间。页面负责按展示范围对文字脱敏，以纯文本显示；已有结论时优先显示结论。旧记录、手动交接或没有过程消息时，只展示已有状态证据。
- 读取失败时保留最后一次成功读取的内容，标明时间、具体原因和可行的下一步，例如重新查询或到指定对话核对。能力只核实了一部分时，保留已接通的动作，为缺失的部分提供手动步骤。

页面必须做到：

- `direct` 为假时，把 `text` 显示出来并提供复制按钮，旁边写“需手动完成”和应粘贴到哪个对话；提供“已粘贴”按钮和粘贴结果的输入框，放在这件事或这个对象旁边。
- 状态可以换成用户的说法，但不能把两档合成一档，也不能说得比 `status` 更乐观；`unknown` 为真时要写出“最新情况未知”。`note` 有内容时要显示。`direct` 为真、状态仍是“需手动完成”且 `unknown` 为真，表示消息可能已经交给 Codex 但没等到确认：这时不要引导用户再粘贴一次，先请他到 Codex 对话里看是否已收到。
- 用户问“为什么是这个状态”时能看到 `events` 里的证据。
- 页面上不提供替用户发送给第三方、提交、付款、发布、删除外部内容的按钮；这些动作写明“由你本人完成”，用户做完后用 `markDone` 记一笔。
- 页面上能看到哪些材料会交出去、哪些能力还没核实。
- 删除或覆盖用户记录前先请用户确认这一次。
- 用户输入和 Agent 返回的文字一律用 `textContent` 之类的纯文本方式显示，不要拼进 HTML。

## 5. 状态从哪里来

| 状态 | 运行支持什么时候写 |
| --- | --- |
| 需手动完成 | 交接内容已生成，还没交出去 |
| 已发送 | 用户点了“已粘贴”；或 Codex 接受了这条消息 |
| 已开始 | Codex 报告这一轮已开始；或这一轮已结束但取回结果还没核实 |
| 已完成 | 拿到了这次要的结果（用户粘贴回来，或从已核实取回的 Codex 对话读到） |
| 待确认 | 拿到了结果，但下一步要用户自己决定（`confirmAfter`）；或结果太长，工作台只保存了前 20000 字（`results` 里这一版带 `truncated`，`note` 会提示到原对话看完整内容） |
| 失败 | Codex 明确报错（例如对话不存在）、消息还没交给 Codex 就出错、这一轮被中断，或用户记下了明确的失败信息 |
| 最新情况未知 | 连接断了、等太久、找不到这一轮或回复文字：保留上一个状态，另外标明未知。消息已经写给 Codex 却没等到确认时也属于这一档，交接上会提示“可能已经交出”，请用户先到 Codex 里看一眼再决定是否重发 |

需手动完成 → 已发送 → 已开始 → 已完成 只往前走。一条交接有了结论之后（已有结果，包括用户自己粘贴回来的；或状态已是待确认、已完成、失败，包括用户自己记下的），平台后来的消息不再改它的状态和结果：后到的“已发送”“已开始”被忽略；同一轮的回复不会再加一版，只在 `note` 里说明它和这里保存的是否一致；重新查询失败也只在 `note` 里提示。`note` 里的提示是追加的，不会冲掉之前的提示。没等到结果不算失败。

## 6. Codex 适配器

只在下面三件事都满足时用 `adapter: "codex"`：

1. 目标由用户明确指定，可以是已有的相关业务对话，也可以是专用对话。按本次授权的材料和动作使用，不从历史里自行挑选目标。建议这些对话使用只读或“需要审批”的权限设置：工作台只能拒绝 Codex 发来的审批请求，对话本身设成不需要审批时，Codex 会直接执行命令，不会来问。
2. 你已在他的环境里核实对应能力（见 [platform-adaptation.md](platform-adaptation.md)）。用户已授权的一次真实工作可以作为该动作的核实依据；需要另测连通性时可用：

   ```bash
   python3 <技能目录>/scripts/workbench.py codex-probe --thread <用户同意用于测试的对话编号>
   ```

   它向这个对话发一句无害的话（“这是个人工作台的连通测试……请只回复：收到”），等这一轮结束再读回回复。发之前要用户同意。打印出“发起：Codex 接受了这条消息”记为发起工作已核实；打印出回复文字记为取回结果已核实。继续同一工作要再用同一对话发第二句并看到回复。
3. 配置里写上对话编号（`thread`）和已核实的能力。

它的做法：每次交接启动一个本机的 `codex app-server`（标准输入输出方式，不经过 shell，不监听网络），对配置里的对话执行 `thread/resume` 和 `turn/start`，等 `turn/completed`；取回结果时优先读这一轮标记为最终答复的文字，旧版使用无阶段标记的回复，`refresh` 时用 `thread/read` 按这一轮的编号查。它用当前环境的 Codex 设置（`CODEX_HOME`），不改这个对话的模型、权限或工作目录。这一轮里 Codex 请求执行命令、改文件或其它权限时，工作台一律拒绝，并在交接上提示用户到 Codex 里处理。它不会新建对话。

每次交接用的 `codex app-server` 由工作台启动，等待结束（默认等待时间到了，或用户关掉工作台）时也会关掉它，Codex 会把这一轮记为被中断。所以长时间的工作不要在这一轮还没结束时关工作台；被中断后状态写“失败”，提示里会说明关闭或超时也会造成中断。

维护者自述：在 codex-cli 0.170.0 上，用隔离的临时配置目录和一个只用于测试的临时对话，用 `codex-probe` 核实过发起和取回各一次，又通过工作台页面接口交付过一次新工作和一次继续同一工作，都取回了回复。测试对话和记录没有随发布包公开。这只是线索，不代表用户的版本或其它 Codex 产品形态也支持；在用户环境里仍要重新核实。

## 7. 交给用户前走一遍

1. `check` 通过，页面能打开，浏览器开发者工具里没有报错。
2. 征得用户同意后，用一条试用内容在页面上走一遍：发起 → 看到“需手动完成”或“已发送” → 粘贴回结果（或等 Codex 返回）→ 看到结果出现在对应位置、状态变化正确。手动交接时，告诉用户这一步需要他把交接内容粘贴到哪里。
3. 直接交付时，在同一次试用中观察进度和结论能否自动出现，核对所属对象和轮次。重新打开页面，应能找回同一条记录及最新结论。缺少过程消息或连接中断时，核对页面显示的最后证据、原因和下一步。
4. 告诉用户试用留下的那条记录在哪里；他要删时按第 4 节先确认再删。

## 8. 安全边界

- 只监听 127.0.0.1；接受的 Host 只有本机地址，用来防止 DNS 重绑定。
- 每次启动生成一个随机令牌，只保存在内存里，注入到页面中；所有接口都要带这个令牌。写操作还要求同源 `Origin`，跨站请求一律拒绝。
- 请求体不超过 256 KB；单段文字不超过 8000 字；单条页面记录不超过 64 KB。
- 只交接到配置里的目标；对话编号只从配置读，页面看不到也改不了。
- `page/` 必须是工作台目录里的真实文件夹；它是指向别处的软链接时，`check` 不通过，工作台也不会启动。
- 页面带内容安全策略，脚本和数据请求只能连本机运行支持，不能加载外部脚本或向外部服务发请求。它挡不住页面跳转到外部网址，所以页面上不要放把内容带到外部的链接。
- 不执行由用户输入拼出来的命令；唯一会启动的外部程序是 `codex app-server`，以参数列表方式调用。
- 状态文件只有本人可读写，日志只记方法、路径和状态码，不记内容。

运行支持不做这些事：替用户发给第三方、提交、付款、发布、删除外部内容；替用户批准 Codex 的任何请求；读取工作台目录以外的文件；决定页面上有什么。
