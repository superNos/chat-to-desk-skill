# 持续调整与规则管理

目标：让工作台跟着用户真实的使用变，而不是越做越大。

## 1. 什么时候回顾

试用期结束时、用户说“不好用”时、或用户的工作明显变化时（换了客户、换了岗位）。回顾使用记录也需要用户授权，范围和历史分析一样要说清。

另外，只要工作模型里某个条目被用户改为已否定（例如“那件事以后不做了”），就把依据它的元素标为“待移除”，下一次调整时请用户确认移除；在确认前，不再围绕这个元素扩展。

## 2. 看哪些使用证据

证据可以来自：工作台自己记下的交接和状态（运行支持保存在工作台目录的 data/ 里）、工作台说明里的调整记录、授权范围内的新对话、用户的直接描述。读工作台记录也要用户同意，和读历史一样说清看什么。直接问用户“这两周哪些用上了、哪些没用”同样是有效的证据，记为用户自述。

- 哪些入口和结果查看被用过、用了几次，哪些从没用过；
- 用户手动改过多少次输入去向，例如把“新工作”改成“继续原来那件”；
- 哪些结果用户仍然要去别处找；
- 哪些工作失败，或长期排队却没有开始；
- 用户在对话里又开始重复交代的背景；
- 成熟流程是否仍要求用户重写步骤、到聊天里催下一步或搬运中间结果；出现这些情况时，检查缺少的是参数、业务操作、产物衔接还是接入能力，不直接再加一个通用输入框；
- 用户口头抱怨或夸过的地方。

## 3. 提出调整

每条建议写成：

```text
建议：去掉“按日期查看”
依据：试用两周没有使用；你找结果时都是按项目地址找
影响：少一个入口，不影响按地址找回
```

可以建议增加、修改或移除。没有使用证据时，不要以“功能更完整”为理由增加东西。移除和简化同样是好的调整。

某个入口一直没用时，先问用户原因再决定，例如：“这两周没有用到‘按日期查看’，是用不上，还是不知道它在哪？”用不上就建议移除；找不到就改放的位置或说法。

## 4. 用户确认后才改

- 用户确认后实施，在依据附录的调整记录里写：版本、改了什么、依据、确认日期。
- 用户拒绝的建议也记下来；出现新的使用证据之前，不再提同一条。
- 一次只改少数几处，改完再试用。

## 5. 规则管理

学到的规则（格式、语气、术语、顺序等做法）放在工作模型的“学到的规则”里，每条都有依据、适用范围和状态。保存规则需要用户的保存授权；有了授权，规则内容也要先经用户在校准中确认，确认前状态写“待确认”，不写“已保存”。

用户可以对每条规则：

| 操作 | 你要做的 |
| --- | --- |
| 保留 | 不变 |
| 修改 | 按用户说法改写，记录修改日期 |
| 限定范围 | 写明只适用于哪位客户、哪类工作，之后只在该范围内使用 |
| 删除 | 立即停用，从工作模型中移除这条规则，交接内容和执行都不再带上；调整记录只写规则编号和删除日期，不保留原文 |

定期（例如每次回顾时）把规则列给用户看一遍，让过时的规则能被删掉。

规则不扩大授权。外部动作统一按 [agent-interaction.md](agent-interaction.md) 第 5 节处理。
