# 从日常工作提炼工作流与功能

在历史分析与用户校准之后、设计页面之前使用。目标是把已经明确的做法变成用户能直接操作的功能，减少重复交代背景、拆步骤和搬运结果。

## 1. 从多次实际交付找稳定做法

按用户要处理的对象与交付目标比较独立事项，识别共同触发、步骤、决定和产物。不能只根据相同关键词、职业或对话标题合并。

- 同一件事跨多个对话修订，只形成一个事项的过程；不能据此创造常用流程。
- 不同事项使用相同方法，或用户明确以后还会用，才能提炼可复用流程。已完成事项可以提供依据，但不重新进入当前工作。
- 相同目标下仅输入变化，可以共用功能；步骤、责任或完成条件不同，应保留分支或分开，不用一个万能提示词掩盖差异。
- 多项操作有明确的材料传递和共同交付目标时，可以形成一个流程。只有先后出现在聊天中，不足以证明必须连起来；无依赖的工作不强行串联。

## 2. 先说明做法，再选择控件

在已有工作模型中为候选流程写清下面的信息，篇幅与实际复杂度相称。不是要求用户填写技术表，也不要求新建一套流程编辑器。

| 要说明的内容 | 需要回答的问题 |
| --- | --- |
| 名称与复用依据 | 用户把它叫什么？哪些独立事项或明确的未来需求支持它？ |
| 触发与交付对象 | 什么时候开始？处理哪一个对象或批次？ |
| 本次变化的输入 | 需要选什么、上传什么或填写什么？已有对象信息能否在授权范围内带入？ |
| 稳定做法 | 已确认的顺序、规则、必要检查和例外分支是什么？哪些信息仍未知？ |
| 分工与决定 | 哪些步骤 Agent 执行，哪些由用户判断或外部系统完成？在哪一步必须停止等待？ |
| 产物与衔接 | 每一步留下什么，下一步使用哪个版本，最终结果放在哪里？ |
| 完成与失败 | 有什么实际证据才算交付？缺材料或失败时从哪里继续，哪些步骤不能重复？ |
| 接入与授权 | 实际调用什么能力？会交出哪些材料？哪些动作未接通或需要本次授权？ |

提炼步骤时区分用户的固定做法与 Agent 在某一轮临时做的检查。只有用户要求、已确认的工作约定、平台权限或下一步执行确实需要的条件，才写成拦截、确认或提醒。沿用原对话中成功处理例外的方式。例如，用户以往能保留草稿继续同步，工作台也应保留草稿继续执行。出现实际冲突时，在受影响的步骤说明原因。

固定背景和规则只有获准保存后才能内化；流程定义不得包含凭据。未知条件先校准或保留待确认，不能照行业惯例补齐。

## 3. 将流程转成工作台功能

先列出用户要完成的操作，再按工作方式选择界面。一个流程可以占一个区域、一个编辑器或若干相关操作，不必压成单个按钮；一个功能也可以整合多个已经确认的后台步骤。

| 用户实际要做什么 | 可选的交互形式 |
| --- | --- |
| 从已有对象中找到要处理的那个 | 使用工作中的识别信息组织列表、搜索或选择器 |
| 提供已知种类的输入 | 有明确含义的字段、文件选择、范围或版本选择；只问本次缺少的信息 |
| 执行固定做法 | 用业务动词命名的按钮，内部携带已确认规则和步骤 |
| 多步骤中作判断 | 展示当前业务阶段、所需材料和下一步操作；无需逐步到聊天中催促 |
| 对比、修改或采用结果 | 对照表、产物预览、编辑区或版本选择；动作绑定当前结果 |
| 处理例外或全新要求 | 在对象旁补充说明，或使用临时安排入口；不自动加入原固定流程 |

这些是选择依据，不是共同栏目。没有已知参数就不造表单，没有跨阶段依赖就不造步骤条；列表、批量操作和周期入口同样需要实际依据。

**成熟流程的正常路径应无需打开聊天窗口，也无需用户重写完整指令。** 仅把历史提示词放进编辑框、给每个对话加一个“继续”按钮、或要求用户在每个步骤重新描述要做什么，都没有完成工作流抽象。自由文本仍可用于材料正文、具体修改意见和例外处理，不为消除文本框而强行结构化。

## 4. 执行绑定业务对象

页面携带流程、对象、输入和已授权步骤，后台再转换为当前 Agent 能执行的请求。用户只需理解业务动作；会话编号、提示词拼装和执行路由留在实现层，按需追溯。

- 多步骤共享同一事项，明确每一步的输入产物和结果版本。已授权的固定内部步骤可衔接执行；遇到用户决定、缺材料、失败或授权边界就停在具体步骤，不让用户猜一段回复意味着什么。
- 保存流程定义版本、本轮参数及执行关联所需的最少信息，后续调整做法不改变旧轮含义。遵守原有保存授权，不复制整段历史。
- 将“事项交付状态”“流程当前步骤”“Agent 本轮状态”区分开。回复结束只说明本轮结束，最终是否完成仍核对用户要求的产物和必要动作。
- 重试只补做失败或未完成部分；已成功且有外部影响的步骤不得盲目重跑。无法确认上轮是否执行时先核实；更换对象或另开批次才建立新事项。
- 下一步只能使用属于该事项、版本明确的已确认产物；迟到的旧轮结果不覆盖当前结论。

流程应由实际工作决定，不要求每个宿主使用相同框架或编排系统。先核实现有运行支持能做到什么，缺少的接入或状态管理必须补齐并验证，不能只写一段提示词就宣称多步骤流程已经接通。

## 5. 验证入口

按 [quality-checks.md](quality-checks.md) 检查代表流程，无需另做一轮验收。

无复用证据时保留一次性工作入口，不为了满足这个检查制造流程。规范修改只需检查受影响的推导与验收条目；实际搭建时再进行真实执行试用，不重复跑所有历史工作。
