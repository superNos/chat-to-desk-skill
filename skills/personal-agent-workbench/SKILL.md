# 个人 Agent 工作台

本技能调用名是 `$personal-agent-workbench`。指导用户自己的 Agent 从授权历史中理解他的日常工作，提炼工作流程，再设计和搭建专属本机工作台。用户通过业务功能处理工作，Agent 在后台执行，结果回到工作对象上。

核心推导顺序是：**授权对话 → 日常工作与具体事项 → 可复用工作流程 → 工作台功能 → 实际执行与结果**。对话是证据和执行载体，不能直接变成导航、功能或工作台的主操作。成熟流程的固定背景、步骤和结果要求应内化到功能；用户只需选对象、补必要参数、作业务决定。新需求和例外情况才需要自由描述。

先读完整个授权范围，跨对话合并同一交付目标，再识别哪些做法在不同事情中复用。随口问答不算工作；一件事聊了很多轮不算多次发生；已办完的事退出当前工作。已完成历史仍可作为流程证据，但只有跨事项实际复用或用户明确未来复用时才形成常用功能。日常工作不能被解释成“每天都做”，也不能仅凭消息时间生成日程或待办。

不同用户应该得到不同的工作台。翻译、教学、招聘、开发、店铺运营的工作台没有共同的固定结构。工作很零散的用户，得到的可能只是一个发起工作的入口和一处找回结果的地方，结论写“暂不需要复杂工作台”；这表示功能少，不表示不做工作台。

## 不可违反的边界

- 主要产出是一个可交互的本机工作台。Markdown 记录或交接文字只能作为工作台里的数据或导出内容，不能代替工作台。用户明确说不要时才停下。
- 没有授权不读历史。分析历史、保存学到的规则、把材料交给 Agent 执行，是三项单独的授权。
- 发送消息或邮件、提交或推送代码、付款、发布、删除、对外提交表单等有外部影响的动作，每次执行前都要用户针对这一次确认。不能从历史习惯、已保存规则或以前的确认推断。
- 工作台里的每个元素（区域、输入框、对象、字段、操作、状态、结果查看、确认动作等）都要能追溯到用户已确认的工作；没有依据就不加。不要套用某种职业或某种布局的现成页面。
- 任务卡、待办、看板、周报、统计图、仪表盘都不是默认起点。证据和用户确认支持时才出现，并使用用户自己的叫法。
- 新建或整体重做 UI 必须实际使用成熟组件库或宿主已有的成熟设计系统，统一核心控件与主题；不能用手写原生控件加少量样式代替。按[设计指南](references/workbench-design.md)选择、实现并验收，组件体系不决定用户的功能和布局。
- 状态只显示有证据的那一档：已发送、已开始、已完成、待确认、失败分开显示；拿不到最新情况时写“最新情况未知”。
- **执行入口必须反向控制 Agent。** 常用流程按钮和临时分派都从页面直接发往已授权的执行目标，自动取得本轮进度与结论。按当前宿主逐项核实发送与回传；不可用的动作标出缺少的连接并禁用。至少一项真实业务从页面发出并自动收到结果才能交付。复制指令、人工粘贴回复不能通过验收。
- 生成需要读取外部事项的动作时，按[平台适配说明](references/platform-adaptation.md)在执行该动作的 Agent 环境中核实只读访问。用户指定编号时，取得与完整编号及授权范围相符的详情，再依据详情给出结论。

- 工作台只在本机打开，不把内容发到外部服务；页面、配置和用户数据放在用户指定的本机目录，不放进技能目录。
- 只保存设计需要的概括和可定位引用，不保存凭据、证件、付款信息或第三方个人敏感信息。用户要求删除时照做并说明删了什么。

## 工作循环

每个阶段结束时，都要让用户确认这一阶段的结果再往下走。用户随时可以停下、跳过或回到前一阶段。

1. **确认范围**：先给用户“第一次使用”的说明，讲清要读什么、存在哪里、不会做什么，取得分析授权；授权后再按 [references/platform-adaptation.md](references/platform-adaptation.md) 只列出授权范围内的对话标题，核实能不能读到历史，读不到就改用粘贴或访谈。读 [references/history-analysis.md](references/history-analysis.md)。
2. **理解工作**：按已确认的平台、项目、时间和排除项遍历全部可访问对话，分批阅读并交代覆盖情况。跨对话归并工作对象、接续关系和反复出现的操作，先按日期还原有证据的工作活动，再整理工作类别、具体事项及其关联，形成带来源的工作模型。首版试用的工作类别可以少，历史覆盖范围仍按用户授权执行。同样按 [references/history-analysis.md](references/history-analysis.md)。
3. **用户校准**：用用户的语言讲出发现，让用户逐条确认、修正、否定或限定范围，并补充历史里看不到的事。读 [references/calibration-interview.md](references/calibration-interview.md)。如果两种解释会改变目标或授权，按[协作 Skill 选择指南](references/skill-selection.md)先做需求探索。
4. **提炼流程并设计工作台**。先读 [工作流抽象指南](references/workflow-abstraction.md)，明确每类工作的触发、可变输入、稳定步骤、人工决定、产物和完成条件，再将步骤映射成业务功能。读 [工作台设计指南](references/workbench-design.md) 和 [交互约定](references/agent-interaction.md)。按[协作 Skill 选择指南](references/skill-selection.md)主动匹配当前宿主可用的技能。校准后候选工作竞争首版范围时先做功能取舍；对已选事项，在画界面前解决流程、交接或完成条件；前端设计使用这些决定和真实结果完成页面。只有当前决策需要时才加载对应技能。根据用户已确认的工作给出草案，让用户看懂从哪里选对象、在哪里操作、在哪里看到结果。从当前运行的 Agent 和可用工具出发，按 [平台适配说明](references/platform-adaptation.md) 逐项核实用户授权的业务动作，接通页面到目标的实际调用。用用户要办的事组织入口、进度和结果，对话作为来源或执行去向。按工作方式选列表、表单、编辑区、业务按钮或结果对照区；不要把每个流程都做成“打开聊天＋预填提示词”。需要用户临时交代具体工作时，再打开分派输入框。
5. **搭建并小范围试用**：只为用户选定的一到三类工作搭建工作台。动手前先读 [references/runtime.md](references/runtime.md)，用附带的本机运行支持搭：按它生成这位用户的页面和配置，放在用户指定的目录。只有用户的电脑确实不能运行 Python 3 时，才按 [references/workbench-design.md](references/workbench-design.md) 第 4 节和用户商量别的做法；你自己的环境不能监听端口或打开浏览器，不是换做法的理由，把启动命令和试用步骤交给用户。让页面在打开时恢复记录，工作中自动同步真实进度，把最新结论放回对应对象和轮次。交给用户前选一个有复用依据的流程，在不打开聊天、不重写完整提示词的情况下走一遍“选对象与参数 → 执行 → 判断结果或处理例外 → 重开找回”；没有复用依据时只试已确认的一次工作，并按 [references/quality-checks.md](references/quality-checks.md) 自查。
6. **持续调整**：根据实际使用提出调整，用户确认后再改；让用户管理学到的规则。读 [references/evolution.md](references/evolution.md)。

需要看“不同证据为何导致不同结论”的示范时，读 [references/cases.md](references/cases.md)。案例只用来理解推理方式，不能复制成当前用户的方案。

## 第一次使用

用户第一次调用时，不要直接读历史或给方案。先用一段普通话说明接下来会怎样，并请用户做选择，例如：

```text
我想先了解你平时用 Agent 做哪些工作，找出你经常重复做、或者事后很难找回结果的事，再和你一起做一个专门给你用的工作台。
如果你同意，我会看看你过去的对话；如果我在这里读不到历史，就请你粘贴几段，或者直接讲讲你平常的工作。
这里的“工作台”是在你电脑上打开的操作页面：常做的事会成为专用功能，你选择要处理的对象、填本次变化的信息，就能执行、看进度和处理结果。临时新要求也能输入。里面放什么由你的工作决定；如果你的工作很零散，它可能只有一个输入框和一处找回结果的地方。
整个过程会分几轮：这一轮我只弄清你的工作，不会马上做东西。
这一步我只读、只整理，不会替你发送、提交或修改任何东西。
开始前请你决定：
1. 我可以看哪些对话？拿不准就先看最近 4 周。有没有要跳过的主题？
2. 我整理出的发现，只在这次对话里给你看，还是保存到你电脑上的一个文件夹？要保存的话留多久？拿不准就先只在这次对话里看。
以后如果要记住你的做法（比如固定的格式要求），或者要把材料交给别的对话处理，我会到时再单独问你。
```

按用户的回答调整说法和范围；用户不熟悉技术时，全程不用字段、接口、页面结构这类词。

用户想跳过分析、直接要一个工作台时，说明没有依据的工作台多半不合用，请他至少讲讲最近两周做过的三件具体的事；他坚持时，按他描述的工作做最小版本，并在工作台说明里写明依据是用户自述。

## 记录与存放

本技能产生三样东西，都由你维护、用户可以审阅：

- **工作模型**：授权范围、按日期还原的活动、工作类别与具体事项、流程定义、证据、校准状态和学到的规则。只记录有依据且设计需要的内容，不建立额外的工时或绩效档案。
- **工作台说明**：结论、页面上每个元素及其依据、输入去向、结果位置、状态规则、需要单次确认的动作、平台能力核实情况、怎么打开、试用范围和调整记录。
- **工作台本身**：一个本机目录，里面是你为这位用户生成的页面和配置，以及工作台运行时保存的记录（见 [references/runtime.md](references/runtime.md)）。

前两个名称是给你用的。对用户可以说“我对你工作的理解”和“工作台使用说明”。

保存授权分开看：用户同意“保存发现”，只表示可以保存观察和证据；工作模型里的“学到的规则”、工作台里需要长期保存的背景资料（固定说明、术语表、格式要求），要等用户另外同意“保存规则”后才写入；在此之前，持久记录里只留编号和“待问”，原文只在当前对话里展示。

存放位置由用户决定，默认只在本机。不要放进会公开或同步给他人的位置，除非用户明确要求。用户只授权分析、未授权保存发现时，工作模型只在当前对话里展示，不写文件。工作台本身和工作台说明，要等用户确认了草案、并说了放在哪里之后才写；那时如果仍未同意保存发现，工作台说明的“依据”只写条目编号和“用户已确认”，不写观察和证据的内容。

## 用户已有的工具

用户可能已经在用某个现成工具管理一部分工作（例如开发者用来分派和跟进多项任务的台账）。只有当它确实对应用户已确认的工作时，才把它作为可选方案提出，由用户决定继续用、只取一部分还是不用；不要把它推荐给工作方式不同的用户，也不要把它的编号、状态或栏目带进其它用户的工作台。
