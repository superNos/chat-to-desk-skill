# 前向演示：两个非开发用户用同一技能得到的工作台

**这是评估演示，不是默认模板。** 这里的页面、区域、字段、按钮和状态只属于两位虚构用户，不能照搬给其他用户，技能文件也不引用本目录。真实使用时，工作台要按当前用户自己的历史和确认结果重新推导。

所有人物、学生代号、问题、日期、对话和页面数据都是虚构的。截图里的 Agent 回复是**模拟**的：由演示人写好后粘贴进工作台，回复开头写着“【模拟 Agent 回复，演示人粘贴】”，这段文字保存在试用记录里。截图顶部的黄条是截图时由演示人另外加上的，不属于 Agent 生成的页面。截图时展开了交接内容和状态记录，方便一张图看全；“记一条新消息”“补充这条消息”等输入表单仍是折叠的。

本演示发生时技能名为 `personal-agent-workbench`，现已更名为 `chat-to-desk`。原始对话与演示产物保留当时名称，下方启动命令和文档链接指向当前目录。

## 演示怎么做

生成后另做了一次展示排版调整：班主任页移除了重复标题说明，两页收紧标题和分隔，分析师页把新问题的输入放在同一行，窄窗口自动换行。字段、交接规则、按钮和试用数据未改；这些视觉调整不是两次独立会话自行生成的结果。

| 项目 | 做法 |
| --- | --- |
| 扮演 Agent 的会话 | 每个场景在独立的临时目录里新开一个 Codex 会话。配置目录也是临时的，只装 `skills/personal-agent-workbench/`（演示时与当时的发布包逐字相同；之后的改动见下文“演示之后对技能的改动”），不加载维护者的全局说明和其它技能，不继承维护者的任何对话上下文。之后每轮在同一会话里续接 |
| Agent 能看到的材料 | 技能文件；用户授权之后放入的 `platform/`（授权范围、平台四项能力核实结果和该场景的虚构历史摘要）；Agent 自己写出的 `output/`。每轮开始时工作目录里有哪些文件，记在 `transcript.md` |
| Agent 看不到的材料 | 场景文件里的 `expected`、`usage_probes`；另一个场景的任何内容；本目录 |
| 用户的回答 | 演示人只转述场景文件 `authorization` 和 `user_calibration` 里的预设回答。预设里没有的问题一律答“说不清”“按你的建议”，或只做流程上的同意（如“可以，请给我看草案”）。第一轮说明和最后一轮“写过程记录”是演示人的话，开头标了“演示说明，不是用户的话” |
| 平台 | 演示环境没有真实的 Agent 平台。两个场景的模拟平台都不是 Codex，也没有本机程序能调用的接口，所以两个工作台都走“复制交接 → 已粘贴 → 粘贴回结果”的手动路径 |
| 隔离 | 两个场景各用一个临时目录、各自的会话，互不读取对方的产物 |
| 页面试用 | 演示用的会话不允许监听本机端口，Agent 搭好后给出了启动命令。演示人用这条命令在本机启动工作台，在浏览器里按 Agent 写的“试用范围”走一遍：发起一件工作，看到“需手动完成”，点“已粘贴”，再把模拟回复粘贴回来，看到“待确认”。E3 另外在同一个问题上“接着查”了一次，停在“已发送（最新情况未知）”。之后用本机 Chrome 无头模式截图，截图前已查看渲染 |

## 产物

| 路径 | 内容 |
| --- | --- |
| `e1-class-teacher/agent-output/工作梳理.md`、`e3-business-analyst/agent-output/工作观察.md` | 工作模型：发现、证据（对话编号）、校准状态和授权 |
| `*/agent-output/工作台说明.md` | 工作台说明：页面上每样东西对应的已确认条目，输入去向、结果回到哪里、状态、每次确认的动作、平台能力、怎么打开 |
| `*/agent-output/workbench.json`、`*/agent-output/page/` | 工作台本身：Agent 为这位用户生成的配置和页面（`index.html`、`style.css`、`app.js`），由技能附带的本机运行支持提供服务 |
| `*/trial-state.json` | 页面试用后工作台保存的记录。记录键里的随机编号已机械替换为 `random1`，其余原样 |
| `*/screenshot.png` | 试用后的工作台截图 |
| `*/agent-output/过程记录.md` | Agent 写的过程记录：各轮问了什么、每个元素的依据、没有放进去的元素及原因 |
| `*/transcript.md` | 由脚本从会话事件中机械提取的逐轮记录：演示人输入原文、Agent 回复原文、Agent 执行的命令首行 |
| [comparison.md](comparison.md) | 两个工作台的差异对比与对应证据 |

发布时做过的机械替换：临时工作目录写成 `<演示目录>`，临时配置目录写成 `<演示配置目录>`（出现在 `transcript.md` 和 E1 的 `工作台说明.md` 的启动命令里）。两份 `transcript.md` 里 Agent 回复中的文件链接，原本指向 `<演示目录>/output/…`，为了能在本仓库里点开，把链接目标机械替换成了 `agent-output/…`，链接文字和其它内容没有改。`agent-output/` 就是演示时的 `output/` 目录，只是没有带上运行时生成的 `data/`，试用记录另存为 `trial-state.json`。

想自己打开某个演示页面，可以在仓库根目录运行（只用虚构数据，监听 127.0.0.1）：

```sh
python3 skills/chat-to-desk/scripts/workbench.py serve --dir evals/personal-agent-workbench/demos/e1-class-teacher/agent-output --open
```

它会在 `agent-output/` 下新建 `data/`，看完可以删掉。

## 运行记录

v0.1.0 的两个演示得到的都是本机文档，用户看过后指出“应该是一个工作台”。技能改为“主要产出必须是可交互的本机工作台”，并附带本机运行支持（见 [CHANGELOG](../../../CHANGELOG.md) 的 0.2.0）。之后两个场景从头重跑了两次，没有手工修改产物。

| 次数 | 发现的问题 | 对技能的修改 |
| --- | --- | --- |
| v0.2 第 1 次 | 两个 Agent 发现自己的环境不能监听端口，就没有用运行支持：一个做成了数据只存在浏览器里的单个离线页面，一个改回文档 | [SKILL.md](../../../skills/chat-to-desk/SKILL.md) 第 5 步、[workbench-design.md](../../../skills/chat-to-desk/references/workbench-design.md)、[runtime.md](../../../skills/chat-to-desk/references/runtime.md) 第 3 节和 [quality-checks.md](../../../skills/chat-to-desk/references/quality-checks.md) 写明：必须用运行支持搭；“你自己的环境不能监听端口”不是换做法的理由，此时给用户一行启动命令和试用步骤 |
| v0.2 第 2 次（本目录） | 两个 Agent 都用运行支持搭出了页面，给了启动命令。下面列出的偏差没有对应的技能缺口，如实保留，没有重跑 | 未改技能 |

### 偏差，如实记录

- **E3 的页面没有“提问同事”一栏。** 场景期望里有“按提问同事整理的答复记录”。E3 的 Agent 只做了“问题名称 + 指标”，每个问题标“待答复/已答复”；用户确认的是“常常同时有三四位同事的问题没答完，需要知道哪些已经答复”，没有说要按同事找。Agent 在说明里写“重复询问时打开旧记录参考，再新建问题重算”，按同事找只能靠问题名称。
- **E3 的平台“发起”和“继续”已核实，页面仍走手动交接。** 模拟平台没有本机程序能调用的接口，Agent 在工作台说明里写明了这一点。场景的使用探针期望“按门店拆开”直接显示“已发送”，演示里先是“需手动完成”，演示人点“已粘贴”后才显示“已发送（最新情况未知）”。这比期望保守，没有更乐观。
- **E3 的 Agent 把运行支持的两个文件复制进了自己的 `output/`，** 启动命令用的是这份副本。副本与演示时技能里的文件逐字相同；本目录没有收录副本，上面的打开命令改用技能目录里的原件。技能没有要求或禁止复制。
- **E1 的周五通知暂缓。** 草案里有，老师选定首版只试家长消息和按学生查找；通知格式要不要长期保存仍是“待问”。`工作梳理.md` 的规则 R1–R3 只写了“待问”，没有内容，因为保存规则还没有授权。
- **E1 用运行支持的“已完成”状态表示“已记录发给家长”。** 只有老师点“我已在工作台之外回了家长”并确认后才会出现，页面上显示的是“已记录发给家长”。
- **两个 Agent 都写了“浏览器走查待完成”，** 因为它们自己不能启动服务。页面试用由演示人完成，见上表。
- **E3 交接里“继续/修改的是哪一件”固定写“原查询”。** 页面在“接着查”和“修改结果”时都把 `about` 写成“原查询”，没有写清是哪个问题的哪一次结果；技能的 `agent-interaction.md` 第 1 节要求写清。页面会另外显示用户填写的原对话定位（只存在本机，不进交接文字），`continues` 也指向上一条交接，但复制出去的交接文字本身不够具体。
- **E3 的模拟回复多说了一条口径。** 演示人写的第一条模拟回复里有“退款单不计入消费”，并说“可以按这个口径答复”。用户确认并获准保存的口径只有“活跃会员＝近 30 天有消费”，退款怎么算从没确认过。这句话只是演示人编的模拟回复，没有写进工作台的口径或配置，但截图读者可能误以为这是用户的规则。这是演示人的失误，保留原记录，没有改写。
- **两份工作台说明都没写结论属于哪一档，平台能力也缺“平台与版本、日期”两项。** 技能的工作台说明示例里有这些内容。
- **E3 的旧交接没有地方贴迟到的回复。** 页面只在一个问题最新的那条交接旁留“带回结果”输入框。第一次查询还没回复、用户先点了“接着查”时，第一次查询的回复到了也没有位置贴回去。演示里第一次查询的结果先回来了，所以截图和试用记录不受影响，但这是这个页面的限制。
- **场景的“通用输入：把上次那个改一下”等探针没有在页面上试。** 演示只走了 Agent 写的试用范围。

## 演示之后对技能的改动

独立复核（v0.2 第 1–5 轮）在演示之后指出了运行支持的几处问题，修改了技能目录里的这些地方，没有重跑演示：

- `scripts/workbench.py`：消息已经写给 Codex、却没等到确认时，不再记为“失败，没有交出去”，改为“最新情况未知”并提示先去 Codex 里看；已有记录不能用 `saveRecord` 悄悄覆盖，要先确认再用 `replaceRecord`；旧版审批请求按协议的写法拒绝；令牌里有非 ASCII 字符时返回 403；同一轮 Codex 工作的结果只保存一次，不会在用户确认后又加一版，后到的“已开始”也不会盖掉“待确认”，用户自己粘贴回结果或记下结论后，平台再来的同一轮回复只做一致性提示，交付途中出错也不改用户已有的结论；结果超过 20000 字时标明只保存了一部分，状态是待确认；已有结论后重新查询失败不改结论；`page/` 是指向工作台以外的软链接时拒绝启动，页面路径里有隐藏目录、或软链接的目标文件类型与地址不符时也不提供。
- `references/runtime.md`：写明上面这些行为；页面要用纯文本方式显示用户和 Agent 的文字；建议接收交接的 Codex 对话用只读或需要审批的设置；关闭工作台会中断 Codex 正在做的一轮；内容安全策略挡不住页面跳转。
- `references/workbench-design.md`、`cases.md`：结论档位统一叫“需要工作台 / 小工作台 / 暂不需要复杂工作台”。
- `references/platform-adaptation.md`：Codex 核实的说法与 CHANGELOG 统一。

两个演示都走手动交接，不经过 Codex 适配器；两个页面都只用 `saveRecord` 写新记录（记录名带随机编号，或在已有记录时不再显示对应输入框），页面也都用 `textContent` 显示文字。所以这些改动不影响演示里 Agent 的推导，演示页面在改动后的运行支持上仍能照常使用，`tests/test_personal_agent_workbench.py` 会对两个演示目录运行 `check`。
